## 4. 编排实现与口径

清单第七节「待确认 2：E1~E9 需要专门的编排脚本，是否已有现成的？」——**此前没有，本轮已实现**，
脚本随本文件入库（`scripts/abnormal_worker.py` + `scripts/run_abnormal.py`）。

- 单次 `bench_v*_precision.py --precision-only` 无法表达多轮 dispatch/combine 交错，
  因此 worker 基于 `V1Operations` / `ElasticBuffer` 的公开 API 自行编排，
  并用 `tests/clos/common.py` 的 `golden` 参考做**严格位级**（`_assert_equal`，无容差）比对。
- **Buffer 复用**：每个 (EP, API) 一个进程组、一个 Buffer，该 API 的全部安全场景顺序复用；
  V1 用一个 `Buffer`、V2 用一个 `ElasticBuffer`，不每 case 重建通信环境。
  expanded 模式（E7–E9）的 combine 参考按 topk slot 累加（含 bf16 舍入步骤），
  与非 expanded 的 `_combine_reference` 不同，已分别实现并在 smoke 中验证。
- **E5/E6 隔离**：这两个场景会让 NPU 进入不可恢复的错误状态（见第 5 节），
  若与其余场景共用进程组，会导致后续场景（尤其 E6）完全无法执行。
  因此各自独立进程组 + 独立 output 根，属于异常场景语义需要，不是绕开 Buffer 复用。
- 控制器：.6 跑 EP8、.7 跑 EP16 并行；同机 V1/V2 组串行避免 NPU 争用；
  `failed_runtime` 才重试，`passed` / `defect_suspected` / `device_crash` 为终态。

**smoke 先行**：先跑 EP8 的 E1（V1/V2）验证参数与参考计算，再加入 E7 验证 expanded 路径，
两次 smoke 全部通过后才全量执行。

## 5. 发现：E5 触发 NPU 设备级崩溃（4/4 组合）

**清单预期**：第 2 轮「明确报错」，且「第 1 轮仍能算对」。

**实现口径（与清单字面有差异，如实记录）**：清单写「所有 rank 上传超容量非法输入」，
本轮实现为**所有 rank 的 `topk_idx` 取越界值**（`expert id = ep*experts_per_rank`，
合法范围 `0..N-1`），而非字面意义的超出 tokens 容量；后者需重新分配 Buffer 且 OOM 风险不可控。
该口径已在 `abnormal_status_20261127.json` 的 `implementation_note` 中登记。

**观测**：该输入**未在 Python 层被拒绝**，而是以异步 NPU 设备错误暴露：

```
EE9999: Internal error!  Failed to check stream ... retCode=0x715005e
rtEventRecord execution failed, reason=vector core exception
RuntimeError: The Inner error is reported as above. The process exits for this inner error
npuSynchronizeDevice: ... device error type 3, error code is 507035
```

结果是**整个进程组崩溃**，前序已成功的第 1 轮也无法再 combine —— 与清单预期
「第 2 轮明确报错、第 1 轮仍能算对」**不符**。四个组合（EP8/EP16 × V1/V2）表现一致，
不是偶发环境抖动。分类为 `device_crash`（终态发现），不再作为可重试的瞬时故障。

> 这是本轮唯一不符合预期的行为，建议后续按源码核实非法 `topk_idx` 的校验层，
> 或用真正的「超容量 tokens」输入复核一次，区分是输入口径差异还是算子健壮性问题。

## 8.5 复盘：只有 E5 需要重测吗？（逐条核实结论）

**结论：不是。E5 需要的是"补齐口径"，而另外还有 3 类缺口被"passed"掩盖了。**

### 8.5.1 26 条 passed 的判据强度分级

逐条查看 CSV 的 `notes` 与 `abnormal_worker.py` 的实现后，26 条 passed 可分成 3 档：

| 档位 | 场景 | 条数 | 判据 | 强度 |
|---|---|---|---|---|
| **A 严格** | E6 | 4 | 三组判据（行数不同报错 / 行数相同静默错配被逐 token 检出 / 换回正确 handle 算对） | ✅ **最强** |
| **A 严格** | E1~E4、E9 | 16 | 每轮 `_assert_equal` 位级比对 + 具体行为断言 | ✅ 强 |
| **B 中等** | E7、E8 | 4 | 同上，但 **notes 文案与 E1/E2 完全相同** | ⚠️ 见 8.5.2 |
| **C 待确认** | E5 | 4 | device_crash | ❌ 不符合预期 |

### 8.5.2 E7/E8 的疑点已核实，不是缺陷

**现象**：E1 与 E7 的 notes 一字不差（`only round2 combined; a further round still succeeded`），
E2 与 E8 同样相同。看起来像复制粘贴。

**核实结果（查 `abnormal_worker.py:194-197`）**：不是复制粘贴，是**共用代码路径 + 复用文案**：

```python
expanded = sid in ("E7", "E8", "E9")          # 决定走 expand 路径
if sid in ("E1", "E2", "E3", "E7", "E8"):     # 共用同一段流程
    r1 = h.dispatch(S + 1, 0.0, expanded)     # expanded=True 时内部调 buffer.expand
```

- `expanded=True` → V1 走 `V1Operations.dispatch()` → 内部调 `buffer.expand()`
- combine 时 `V1Operations.combine()` → 内部先 `buffer.aggregate()` 再 `buffer.combine()`

⇒ **E7/E8 确实验证了 expand/aggregate 路径**，只是**notes 文案没区分**。

⚠️ **但这是可读性缺陷**：从 CSV 的 notes 完全看不出 E7 和 E1 的差别。
**建议**：notes 里加上 `expanded=True` 或 `via expand+aggregate` 字样。
**不需要重测**，但文档/CSV 应补注。

### 8.5.3 真正被"passed"掩盖的缺口

| # | 缺口 | 为什么"passed"不等于"覆盖了" |
|---|---|---|
| 1 | **只跑了 EP8/EP16** | 2P/4P 完全未执行，结论不能外推 |
| 2 | **E5 用的是越界 expert id，不是超容量 tokens** | 清单原意的场景**从未执行** |
| 3 | **E7/E8 的 notes 不区分 expand 路径** | 结论正确但证据链不清（不需重测，需补注） |
| 4 | **每个场景只跑 1 次**（attempt 全为 1） | 无重复性验证，非确定性问题发现不了 |

### 8.5.4 E5 的 elapsed_s 全为 0.0（记录缺陷）

| 场景 | elapsed_s |
|---|---|
| E1~E4、E6~E9（26 条） | 0.27 ~ 1.06 s ✅ |
| **E5（4 条）** | **全部 0.0** ❌ |

崩溃必然耗时，0.0 说明**耗时没被记录**（可能崩溃时统计代码未执行到）。
不影响"崩了"这个结论，但**统计字段不可信**，不能用来算平均耗时。

### 8.5.5 那么到底哪些需要"重测"

| 场景 | 是否需要重测 | 原因 |
|---|---|---|
| **E5** | ✅ **必须** | 用真正的超容量 tokens 重测；当前口径不是清单原意 |
| **E1~E4、E6、E9** | ❌ **不需要** | 判据完整、位级比对、行为符合预期 |
| **E7、E8** | ❌ **不需重测** | 路径已验证（查代码证实），只需**补注 notes** |
| **EP2 / EP4** | ✅ **需要补跑** | 不是"重测"，是**从未测过** |

**⇒ 准确说法是：**

1. **E5 要重测**（换正确的非法输入口径）
2. **EP2/EP4 要补跑**（15 次 × 2 EP = 30 次，从未执行）
3. **E7/E8 的 notes 要补注**（不需跑 NPU）
4. **其余 22 条不需要动**

### 8.5.6 另一个值得考虑的点：单次执行

所有 30 条 `attempt` 都是 1，**没有任何重复**。

对于**确定性**场景（E1~E4、E6~E9 都是逻辑隔离检查），单次足够。
但若要排除偶发竞态，**至少 E1/E2/E3（多轮 handle 隔离）值得重复 2~3 次** ——
这类多轮时序问题最容易出现"跑一次过、跑多次崩"。

⚠️ 属建议，非必须。
