# R3 补充：EP4 / EP64 性能（基于 1128 实测原表，2026-11-28）

> 用户指令：「基于1128的性能表，补充ep4和ep64性能，node7不测性能，换其他空闲机器」。
> 经确认 **node7 指 `30.104.128.7`（node3，之前说「性能有问题」那台）**，补测继续排除它；
> 「换其他空闲机器」= EP64 原分配含被别人占的 `.4/.5`，改用空闲机。
> 表的选择（用户确认）：用 **`baseline/EP4-128_通信带宽_20261128.txt`（1128 实测原表，18 例/EP）**，
> 不是 `baseline/V2测试Case_20261128快照.txt`（基线侧，12 例/EP）——原表明确标注两批数据勿混用。
> 入口：[`scripts/run_round3.py --supp`](./scripts/run_round3.py)、[`scripts/auto_start_supp.py`](./scripts/auto_start_supp.py)、
> 规格 [`scripts/perf_cases_supp.json`](./scripts/perf_cases_supp.json)。

## 1. 用例来源与规模

[`baseline/EP4-128_通信带宽_20261128.txt`](./baseline/EP4-128_通信带宽_20261128.txt)
是 1128 **实测原始表**（108 数据行 = 6 EP × 18 例）：

每 EP **18 例** = 3 Tokens/rank(4096/8192/16384) × 3 Hidden(2816/6144/7168) × 2 AIV(8/32)；
Experts 恒 **256**、TopK=8、GB/s/rank 仅计通信 kernel。
固定 bf16 / expand=1 / uniform / warmup=10 / iterations=30 / seed=20260823（沿用 R3 主性能口径）。

| EP | 表中 | 例数 | epr | 拓扑 |
|---|---|---|---|---|
| **EP4** | 有 18 例 | **18** | 256/4 = **64** | 1 机 × 4 卡 |
| **EP64** | 有 18 例 | **18** | 256/64 = **4** | 4 机 × 16 卡 |

- `--ep-size=4`、`--aiv=8/32`、`--num-tokens=4096` 均在 `bench_v2_bandwidth.py` 合法范围内，
  已在新 wheel 容器内用 `arguments()` 逐项验证（6 组组合全 OK）。
- 补测用**独立** [`scripts/perf_cases_supp.json`](./scripts/perf_cases_supp.json)，
  `perf_cases(..., supp=True)` 读它；**基线 [`scripts/perf_cases_v2.json`](./scripts/perf_cases_v2.json) 完全未改动**
  （`axes.ep_size` 仍为 `[8,16,32,64,128]`，60 例基线不变）。
- EP4 的 topk=8 ≤ min(128, EP×epr)=min(128, 256)=128，合法；hidden 均 128 倍数。

## 2. 节点分配（「换其他空闲机器」）

| EP | 原分配 | **补测分配** | 说明 |
|---|---|---|---|
| EP64 | `[0,1,2,4]` = `.4/.5/.6/.8` | **`[2,4,5,6]` = `.6/.8/.9/.10`** | 原分配含被别人 AngelPTM 占的 `.4/.5`，换成 4 台空闲机 |
| EP4 | 无 | **`[7]` = `.11`** | B 收尾后空闲，单机 4 卡 |

- 两组节点不重叠 → **一波并行**（`perf_waves` 的 `supp` 分支输出 `EP64 + EP4`）。
- **`.7`（node3）不参与**：`perf_argv` 里 `assert 30.104.128.7 not in hosts` 硬断言，
  补测节点均不含它（EP4 用 `.11` 不是 `.7`）。
- **`.4/.5` 不参与**：补测自动启动器只等 `.6/.8/.9/.10/.11` 五台 16/16 空闲，
  不依赖 `.4/.5` 释放，因此可与 C 守护（等 8 台全空闲）并行等待、不抢卡。

> 备注：`node7` 在 R3 编号里是 `.11`（node 号 = IP 末位 − 4），而用户确认本指令里的
> 「node7」指 IP `.7`。补测 EP4 用的是 `.11`，两者不冲突；文档统一写 IP 避免歧义。

## 3. 触发与重试

[`scripts/auto_start_supp.py`](./scripts/auto_start_supp.py)：

1. 等 **B 控制器**（`run_round3.py perf --eps 8,16,32`）退出（B 已完成 36/36）；
2. 等补测所需 5 台（`.6/.8/.9/.10/.11`）全部 16/16 空闲；
3. 无其它补测控制器在跑 → 启动 `run_round3.py perf --eps 4,64 --supp`；
4. 监控控制器进程：被 kill / 异常退出且 `round3_perf_supp.csv` 未满 36 例即重启；
5. `round3_perf_supp.csv` 出现 **36** 个不同 `run_id`（18 例 × 2 EP，每 case 4 个 op 行）→ 完成。

与 C 守护的关系：C 守护 `auto_continue_c.py` 要求「8 台全空闲 + B 退出 + 无其它控制器」，
补测占着 `.6~.11` 时 8 台不全空闲，C 不会提前触发；补测退出后 C 守护继续按
`.4/.5` 释放时机接续 EP128。两个守护各自只识别自己的控制器，互不误判。

> 2026-11-28 修正：`auto_continue_c.controllers()` 原先只认 `python3` / `/opt/conda` 前缀，
> 漏掉补测控制器实际的 `/usr/bin/python3 -u run_round3.py ...`，而补测 case 之间存在
> NPU 全部显示空闲的瞬态窗口——`.4/.5` 一旦释放，C 有可能误判 8/8 空闲并与补测撞车。
> 现按 argv[0] basename 以 `python` 开头判定，并把 `run_perf_reuse.py`（复用版性能控制器）
> 一并纳入「其它控制器」检测；C 守护已用新代码、8h 窗口重启。

## 6. 第二套：「复用统一 Buffer」版（两套对比）

> 用户指令：「性能也复用统一buffer」→ 澄清选择「**两套都跑做对比**」：
> 保留第 1~5 节的官方原口径（每 case 独立进程组 + 独立 Buffer）结果，
> 另跑一套「持久进程组 + 分组复用 Buffer」的同 36 例，出两份 CSV 对比。

入口：[`scripts/r3_perf_reuse/run_perf_reuse.py`](./scripts/r3_perf_reuse/run_perf_reuse.py)、
[`scripts/r3_perf_reuse/reuse_worker.py`](./scripts/r3_perf_reuse/reuse_worker.py)，
规格仍用 [`scripts/perf_cases_supp.json`](./scripts/perf_cases_supp.json)。

**测量口径零改动**：`reuse_worker.py` 只在本进程内 monkeypatch，不改任何容器内源码：

| patch | 官方 `worker()` 里的点 | 改成 |
|---|---|---|
| `dist.init_process_group` / `dist.destroy_process_group` | `bench_v2_bandwidth.py:427` / `:717` | no-op，持久进程组只建一次 |
| `deep_ep.backends.global_clos.ElasticBuffer` | `:428`（函数内 `from ... import`） | 按组缓存实例的工厂 |
| 工厂返回 `_NoDestroy` 代理 | `:699` `buffer.destroy()` | 吞掉，真实 Buffer 组末统一 destroy |

组内每个 case 仍调用官方 `B.worker(args)`：profiling / warmup=10 / iterations=30 /
精度校验 / `byte_ledger` 全部沿用；GBps 用官方 `summarize()` 的 per-rank 公式
`official_logical_GBps = official_logical_bytes / mean(samples.comm_us) / 1000`，
rank0 `all_gather_object` 汇总 mean/min/max。

**分组**：按 `(hidden, num_topk, dtype, huge_pages)` 分组，组内 6 例复用一份 Buffer，
`num_max_tokens_per_rank` 取组内 max = **16384**；组边界 destroy。
EP4 / EP64 各 18 例 → 各 **3 次** Buffer 初始化（原口径各 18 次）。
> 注意：`num_max_tokens_per_rank` 被抬到 16384 是「一份 Buffer 覆盖组内所有 case」的必要
> 代价，会在两套对比里作为**已知的额外变量**单独标注；测量输入张量仍按各 case 的
> `num_tokens` 构造，不受影响。

**Smoke 验证**（2026-11-28，`.11` 单机 EP4，3 例 / 2 组）：

```
REUSE_PASSED rank=0..3 buffer_inits=2 cases=3
buffer_reused: false / true / false
```
`summary_reuse.csv` 12 行（3 例 × 4 op），`reuse_rank0.json.state=passed`。
同形状对第 1 套原口径结果：`dispatch 111.07` vs `111.343`、
`cached-dispatch 122.418` vs `122.451`（GB/s/rank，差异 <0.3%），口径一致。

**触发与重试**：等 `round3_perf_supp.csv` 满 36 个 `run_id` + 5 台全空闲 +
无其它控制器；每轮 attempt 用独立 `rdzv-id` 与独立输出目录（官方 worker 的
`mkdir(exist_ok=False)` 不允许复用目录），只跑 `round3_perf_supp_reuse.csv` 里
尚缺的 variant；被 kill / 出错按 checkpoint 续跑，`--max-attempts 6`。

| 产物 | 内容 |
|---|---|
| `round3_perf_supp_reuse.csv` | 第二套逐 op 行（列同第 1 套 + `buffer_reused` / `buffer_initializations_so_far` / `elapsed_s` / `mode=reuse`） |
| `round3_reuse_status.json` | 控制器状态，按 .gitignore 不入库 |
| `/tmp/r3_reuse_4_64.*.log` | 逐 attempt 逐节点日志 |

节点沿用第 2 节（EP4→`.11`，EP64→`.6/.8/.9/.10`），同样排除 `.7` 与 `.4/.5`；
纯 auto（`env -u DEEPEP_CLOS_QP_PLANS`，不注入 timeout），不加 `--huge-pages`。
