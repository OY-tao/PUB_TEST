## 3. E5 修正的源码依据（关键）

| 版本 | 校验点 | 触发条件 |
|---|---|---|
| V1 | `buffer_v1.py:508-509` `raise ValueError("local token count exceeds num_max_tokens_per_rank")` | `self.num_max_tokens_per_rank is not None` **且** `x.size(0) > capacity` |
| V2 | `elastic_v2.py:1378` `raise ValueError("x.size(0) exceeds num_max_tokens_per_rank")` | `x.size(0) > capacity` |

⚠️ **v1 worker 的 V1 Buffer 只传了 `num_nvl_bytes`，没有传 `num_max_tokens_per_rank`**
→ V1 的容量校验**从未启用**。v2 显式传入 `num_max_tokens_per_rank=16384`。

v2 的 E5 输入与预期：

| 项 | 值 |
|---|---|
| 正常场景 `num_tokens` | 1024 |
| `capacity` (`num_max_tokens_per_rank`) | 16384 |
| 第 2 轮非法输入 | `num_tokens = 16385`（capacity+1），**所有 rank 一致** |
| `topk_idx` | 值域合法 `0..num_experts-1`（不再是越界 expert id） |
| 预期 | Python 层 `ValueError` 含 `exceeds num_max_tokens_per_rank`，且**第 1 轮 combine 仍算对** → 分类 `passed` |
| 若未拒绝 / 第 1 轮失败 / 设备崩溃 | `defect_suspected` / `failed_runtime` / `device_crash` |

这才对应清单原文「第 2 轮明确报错，第 1 轮仍能算对」。

## 7. 执行前需人工确认的风险

1. V1 `Buffer` 新增 `num_max_tokens_per_rank` 会改变 shmem bootstrap 参数；建议先 `--eps 2 --only E1` 做最小 smoke。
2. V1 的 `get_dispatch_layout` 在 `buffer.dispatch` **之前**执行，超容量 `topk_idx` 有可能先被别处拦截，导致错误信息不含容量校验关键字 → v2 会记 `defect_suspected`，需人工看日志复核。
3. `capacity+1 = 16385` tokens 的 x 约 67 MB/rank（BF16），EP16 合计约 1 GB；内存可控但仍需 preflight。
4. `--repeat` 使总执行次数 ×N，耗时相应增加。
5. 执行前需确认 .6/.7 空闲：EP64 泛化精度仍 `paused`（351/400），四机可能被其他任务占用。
