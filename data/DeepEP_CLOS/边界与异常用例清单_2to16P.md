## 〇、官方约束（用户提供，2026-11-27）

**这是真正的算子契约，优先级高于我之前所有的推断。**

### 四条参数约束

| 参数 | 限制 |
|---|---|
| **EP 数** | **2 ~ 1024** |
| **专家数 E** | `E % EP == 0` 且 `4×(align_up(EP,8) + align_up(E,8)) + align_up(EP,32) ≤ 221120` |
| **Hidden size H** | **BF16 dispatch → BF16 combine：H ≤ 98304**<br>**FP8 dispatch → BF16 combine：H ≤ 109536** |
| **token per rank S** | 小于 `num_max_tokens_per_rank` 配置即可 |

`align_up(x, y)` = 把 x 向上对齐到 y 的倍数。

### 0.1 与我此前结论的对照（我错了）

| 项 | **官方约束** | 我之前写的 | 差异 |
|---|---|---|---|
| H 上限（BF16） | **98304** | 7168 | **我少了 13.7 倍** |
| H 上限（FP8） | **109536** | 7168 | **我少了 15.3 倍** |
| EP 上限 | **1024** | 256（bench choices） | 官方允许更大，**bench 层更窄** |
| S（tokens） | `< num_max_tokens_per_rank` | 16384 | 官方**无固定值**，取决于配置 |

⚠️ **我此前说"源码无 H 上界"是按 Python 层查的。**
实际情况：**Python 层确实不校验，但 C++/kernel 层有 98304 / 109536 的硬限**。
这三个数字（98304、109536、221120）**在开源 Python 代码里完全搜不到**，
所以只查 Python 源码会得出"无上界"的错误结论。

### 0.2 专家数公式的实际强度

把公式代入各档 EP（取 E = EP）：

| EP | E | `4×(au(EP,8)+au(E,8))` | `au(EP,32)` | 合计 | ≤221120 |
|---|---|---|---|---|---|
| 2 | 2 | 64 | 32 | **96** | ✅ |
| 8 | 8 | 64 | 32 | 96 | ✅ |
| 32 | 32 | 256 | 32 | 288 | ✅ |
| 128 | 128 | 1024 | 128 | 1152 | ✅ |
| 1024 | 1024 | 8192 | 1024 | **9216** | ✅ |

**即使 EP=E=1024，合计也只有 9216，不到上限 221120 的 5%。**

求解公式的饱和点：

| 固定 | 求解 | 结果 |
|---|---|---|
| EP=8 | E 最大 | **约 55264** |
| E=1024 | EP 最大 | **约 43400** |

⇒ **公式是"宽松兜底"，真正的约束是 `EP ≤ 1024` 和 `E ≤ 1024` 本身。**
在 2~1024 范围内，该公式**永远满足，不会拒绝任何用例**。

⚠️ 这意味着：**公式不该作为测试用例的设计依据**（它测不出东西），
但**必须写进文档**，因为它是官方契约的一部分。

### 0.3 H 上限的验证难点

98304 和 109536 都不是 bench 参数层能校验的：

| 层 | 是否校验 H 上界 |
|---|---|
| 库文档 | 声明 7168（**与 98304 矛盾**） |
| bench 参数层 | 只查 `hidden % 128` |
| Python 算子层 | 只查 `hidden > 0` |
| **C++ / kernel 层** | **有 98304 / 109536 硬限**（无法从 Python 侧看到） |

**⇒ 要测 H 的真实上限，只能实测逼近**：
从 7168 开始倍增（14336 / 28672 / 57344 / 98304），看在哪一档开始失败。

⚠️ H=98304 时单 rank BF16 payload = `98304 × 2 = 192 KiB/row`，
若 tokens=8192，则 **1.5 GiB/rank**，8 卡就是 12 GiB —— **很可能先 OOM，而不是撞 H 上限**。
所以 H 上限测试必须用小 tokens（如 1 或 64）隔离变量。

## 一、边界来源核实：三个不同的"边界"，不能混用

⚠️ **2026-11-27 修正**：初版边界表把**库文档**的推荐值当成了**算子校验**，
已回源码逐条核实。三者不一致，必须分清在哪一层生效。

### 1.1 三个来源的区别

| 来源 | 是什么 | 在哪生效 | 能否作判据 |
|---|---|---|---|
| **库文档**（`docs/elastic.md` 等） | 官方声明的支持范围 | 无强制力 | ❌ 只作参考 |
| **bench 参数校验**（`bench_v2_bandwidth.py:137-141`） | 基准脚本的入参检查 | 参数解析阶段 | ✅ 但只管 bench 能跑什么 |
| **算子源码校验** | 真正的 API 契约 | dispatch/combine 调用时 | ✅ **真正的算子边界** |

### 1.2 逐项核实结果

| 项 | **算子源码真实校验**（核实自源码） | 库文档 | 我初版写的 |
|---|---|---|---|
| `hidden` 上界 | **无上界**。V2 只查 `hidden > 0`（`elastic.py:230`） | 7168 | ❌ 7168 |
| `hidden` 对齐 | V2 **无 %128 强制**；`x hidden size` 只与 Buffer 构造值比对（`elastic.py:1380`） | BF16 16 / FP8 128 | ❌ 写成硬约束 |
| `num_topk` 上界 | **V2: `_MAX_TOPK = 128`**（`elastic.py:45,415`）；V1 未见显式校验 | V1 16 / V2 32 | ❌ 16 / 32 |
| `num_tokens` 上界 | **无上界**。只查 `> 0` 且 `≤ num_max_tokens_per_rank`（`buffer.py:110,509`） | 16384 | ❌ 16384 |
| 专家数 `E` | **无显式上界**。V2 要求 `num_experts % world_size == 0`（`elastic.py`） | ≤1024 | ❌ ≤1024 |
| `num_experts` 上限 | `_MAX_LOCAL_EXPERTS_FOR_SIZE_HINT = 1024` —— **仅用于 size hint 估算，不是校验** | 1024 | ❌ 当成硬约束 |
| 节点内 rank | `_MAX_SHMEM_INTRANODE_RANKS = 1024` —— **是 rank 数，不是专家数** | — | 初版完全没提 |
| `num_aiv` 上界 | `_MAX_NUM_AIV`：**架构 3510 → 64，2201 → 48**（`config.py:22-27`） | — | 我按 64 写 |

### 1.3 三条必须改正的误解

**误解 1：hidden ≤ 7168 是算子限制**

错。7168 是**文档推荐上限**，源码只查 `hidden > 0`。
真正的限制来自 **bench 参数层**（`hidden % 128`）和 kernel 内部 workspace 预算。

**误解 2：`1024` 是专家数上限**

错。源码里两处 1024 都不是专家数校验：

```python
_MAX_SHMEM_INTRANODE_RANKS     = 1024   # 节点内 rank 数上限
_MAX_LOCAL_EXPERTS_FOR_SIZE_HINT = 1024   # size hint 估算用的上界，仅影响 workspace 预估
```

**误解 3：topk ≤ 32**

错。V2 的真实上限是 **`_MAX_TOPK = 128`**（`elastic.py:45`）。
32 是**文档**的说法；bench 参数层用的是 `min(128, ep×epr)`。
⇒ 三处口径：文档 32、源码 128、bench `min(128, ep×epr)`。

### 1.4 那"边界测试"到底该测什么

既然源码没有形状上界校验，**真正的边界就不在参数层，而在以下几处**：

| 真实边界类型 | 位置 | 怎么测 |
|---|---|---|
| **workspace / 显存预算** | kernel 内部，`get_buffer_size_hint` | 逐级放大 hidden/tokens 直到构造失败 |
| **bench 参数层** | `bench_v2_bandwidth.py:137-141` | `hidden % 128`、`topk ≤ min(128, ep×epr)` |
| **V2 整除契约** | `elastic.py` | `num_experts % world_size != 0` 应报错 |
| **topk 真上限** | `_MAX_TOPK = 128` | topk=129 应报错，topk=128 应通过 |
| **token 容量** | `num_max_tokens_per_rank` | 超容量应报 `local token count exceeds...` |
| **路由采样** | `route_workloads.generate` | `k > ep×epr` 时 Python 抛 `ValueError` |

⚠️ **结论：初版的 S1~S8 里，只有 S1（tokens=1）、S4（FP8 hidden=128）、S5（hidden=7168）
算"有意义的边界"，其余几条要么在参数层就被拦、要么根本不是算子边界。**

### 1.5 已修正的用例设计原则

新原则：**每条边界用例必须写明"在哪一层验证"和"预期错在哪一层"**。

| 用例 | 验证层 | 判据 |
|---|---|---|
| hidden=7168 | kernel 预算 | 正常出结果 |
| hidden=7169 | bench 参数层 | `hidden % 128` 不过 → p.error |
| hidden=8192 | kernel 预算 | `8192%128==0` 能过 bench，**看 kernel 是否 OOM** |
| topk=128 | 算子 `_MAX_TOPK` | 应通过 |
| topk=129 | 算子 `_MAX_TOPK` | 应报 `num_topk must not exceed 128` |
| experts=3 (EP2) | V2 整除契约 | `3 % 2 != 0` → 应报错 |
| tokens 超容量 | `num_max_tokens_per_rank` | 应报 `local token count exceeds` |

## 二、形状边界用例（按官方约束重设，每个 EP 8 条）

**依据**：第〇章的官方约束，而非我此前推断的 7168 / 16384。

### 2.1 H 上限逼近（H1~H5）

⚠️ **必须用 `tokens=1`** —— H=98304 配 tokens=8192 会占 1.5 GB/rank，先撞显存而非 H 上限。

| # | H | tokens | dtype | 预期 | 验证什么 |
|---|---|---|---|---|---|
| H1 | **7168** | 1 | bf16 | 正常 | 文档推荐值（基线对照） |
| H2 | **14336** | 1 | bf16 | 正常 | **2× 文档值，验证"7168 不是硬限"** |
| H3 | **49152** | 1 | bf16 | 正常 | 半程 |
| H4 | **98304** | 1 | bf16 | 正常或边界失败 | **BF16 官方上限** |
| H5 | **98432** | 1 | bf16 | **应失败** | 上限 +128，验证是否真在 98304 卡住 |

### 2.2 FP8 的 H 上限（H6~H7）

FP8 上限比 BF16 高（109536 vs 98304），这是**两种 dtype 的关键差异**。

| # | H | tokens | dtype | 预期 | 验证什么 |
|---|---|---|---|---|---|
| H6 | **107008**（>98304, <109536） | 1 | fp8 | 正常 | **BF16 该失败、FP8 该通过的分界区间** |
| H7 | **109536** | 1 | fp8 | 正常或边界失败 | **FP8 官方上限** |
| H8 | **109664** | 1 | fp8 | **应失败** | 上限 +128 |

⚠️ **H6 是整组里最有价值的一条**：它落在 98304~109536 之间，
**同一 H 下 BF16 应失败、FP8 应通过** —— 直接验证两个上限的差异是否真实存在。

### 2.3 tokens 边界（S1~S2）

| # | S | H | 预期 | 验证什么 |
|---|---|---|---|---|
| S1 | **1** | 7168 | 正常 | 下界 |
| S2 | **超过 `num_max_tokens_per_rank`** | 7168 | 报 `local token count exceeds` | **算子真校验**（`buffer.py:509`） |

⚠️ S2 需要显式构造：Buffer 构造时 `num_max_tokens_per_rank=N`，
dispatch 时传 tokens=N+1。**bench 不暴露该参数**，需绕过 bench 直接调 API（见第〇章 0.3）。

### 2.4 与旧版的对照

| 旧用例 | 问题 | 新版 |
|---|---|---|
| S3 hidden=16 | bench `%128` 必拒 | ❌ 删除（测不到算子） |
| S5 hidden=7168「上限」 | **7168 不是上限，是推荐值** | 降为 H1 基线对照 |
| S7 hidden=8192 | 以为是"超上限" | ✅ **它远低于真上限 98304，应正常** |
| S8 hidden=16384 | 以为是"极大值" | ✅ **仍远低于上限，应正常** |

⚠️ **注意 S7/S8 的语义完全变了**：按旧认知它们是"超限探测"，
按官方约束它们是**完全合法的正常形状**。
这正好说明**我之前的边界设计基于错误的假设**。

## 三、专家边界用例（按官方约束重设，每个 EP 8 条）

**依据**：`E ≤ 1024`、`E % EP == 0`、`4×(au(EP,8)+au(E,8))+au(EP,32) ≤ 221120`。

### 3.1 E 的上限逼近（X1~X4）

| # | E | epr | topk | 预期 | 验证什么 |
|---|---|---|---|---|---|
| X1 | **EP**（=P） | 1 | 1 | 正常 | E 下界，每卡 1 专家 |
| X2 | **1024** | 1024/P | 8 | 正常 | **E 官方上限** |
| X3 | **2048** | 2048/P | 8 | **应失败** | 上限 ×2，验证是否真在 1024 卡住 |
| X4 | 1024 | 1024/P | 1 | 正常 | topk 下界配 E 上限 |

⚠️ **X3 需要谨慎**：`epr = 2048/EP`，EP=2 时 epr=1024，E=2048。
文档说 E≤1024，预期应报错——但**具体报错点不明**（Python 层无校验，
可能到 kernel 才失败，也可能是 OOM 而非参数拒绝）。**必须记录实际失败形态**。

### 3.2 整除契约（X5~X6）

| # | E | EP | E%EP | 预期 | 验证什么 |
|---|---|---|---|---|---|
| X5 | **1023** | 2 | 1 | **应报错** | 不整除 |
| X6 | **1026** | 2 | 0 | 可能失败 | 整除但超 1024 |

⚠️ **X5 可行、X7（之前想的"奇数 E"）不可行**：
`E = EP × epr` 中 epr 必须是整数，所以 **E 必然是 EP 的整数倍**，
`E % EP != 0` **永远构造不出来**——除非绕过 bench 直接构造 Buffer
（`ElasticBuffer(num_experts=1023)` 而不通过 epr 推导）。

⇒ **X5 必须绕过 bench**，用直接 API 调用传 `num_experts=1023`。

### 3.3 公式约束（X7~X8）—— 实测确认它不会拒绝

| # | EP | E | 公式值 | 预期 | 验证什么 |
|---|---|---|---|---|---|
| X7 | **1024** | 1024 | 9216 | 正常 | 公式在最大合法点仍远低于 221120 |
| X8 | 1024 | 1024 | 9216 | 正常 | 同 X7 但 topk=128（配 3.4 节） |

⚠️ **X7/X8 的价值是"证伪"而非"发现"**：第 0.2 节已算出公式是宽松兜底，
即使 EP=E=1024 也只用到上限的 4.2%。**这两条的作用是实测确认这个推算**，
而不是期待它报错。

### 3.4 topk 高位（补充，见 3.5 节分析）

官方**没有给出 topk 上限**（我此前从源码查到 `_MAX_TOPK=128`，
但那是 Python 实现细节，官方契约未声明）。

| # | topk | E | 预期 | 说明 |
|---|---|---|---|---|
| T1 | 48 | 512 | 正常 | 跨过文档曾说的 32 |
| T2 | 96 | 512 | 正常 | |
| T3 | **128** | 512 | 正常 | 源码 `_MAX_TOPK` 值 |
| T4 | **129** | 512 | **bench p.error** | 越 bench 参数层 |
| T5 | **256** | 512 | **？** | **越过源码 128，看真实行为** |

⚠️ **T5 是本组最有价值的探测**：如果官方没有 topk 上限，
那么 256 应该能跑（源层的 128 只是 Python 侧的限制）；
如果失败，则说明 kernel 确实有 128 的硬限。

### 3.5 与我此前分析的对照

| 项 | 我此前 | 官方约束 |
|---|---|---|
| E 上限 | 无显式上界（Python 层） | **≤1024（有明确上限）** |
| E 整除 | V2 要求 `E % world_size == 0` | **`E % EP == 0`**（同义） |
| 公式约束 | **完全不知道** | `4×(au(EP,8)+au(E,8))+au(EP,32) ≤ 221120` |

⚠️ **官方约束里没有 topk 上限**，这与我查到的源码 128 不矛盾——
可能是"官方不承诺、实现上有软限"。**需要 T5 实测确认。**

## 三·五、泛化用例对**官方约束**的覆盖（重新核查）

⚠️ **本节已按第〇章的官方约束重写。** 之前基于"7168 是上限"的核查结论作废。

### 3.5.1 按官方约束看，覆盖缺口比想象的严重得多

| 维度 | 官方范围 | 泛化实际覆盖 | 覆盖率 |
|---|---|---|---|
| **EP** | 2 ~ **1024** | 2 ~ **16** | **1.6%** |
| **H** | ≤ **98304**（BF16） | ≤ **7168** | **7.3%** |
| **E** | ≤ 1024 | 2 ~ 1024 | **100%** ✅ |
| **公式** | ≤221120 | 全部满足 | 100% ✅ |
| topk | 官方未声明 | 1~32 | — |

**E 维度的覆盖是完整的**（最大到 1024，正好撞上限），
但 **EP 和 H 两个维度的覆盖都不到 10%**。

### 3.5.2 H 维度的空洞最大

| H 区间 | 泛化覆盖 |
|---|---|
| 128 ~ 7168 | ✅ 8 档稠密 |
| **7169 ~ 98304** | ❌ **完全空白（上限是当前最大值的 13.7 倍）** |

**这是最大的测试盲区**：官方允许到 98304，泛化只测到 7168，
**上限是已测最大值的 13.7 倍，中间这一段一发未测**。

若 kernel 在大 H 下有正确性问题（如 tiling 溢出、workspace 不足），
**当前 200 条泛化全部发现不了**。

### 3.5.3 EP 维度的空洞

| EP | 泛化覆盖 |
|---|---|
| 2 / 4 / 8 / 16 | ✅ |
| **32 ~ 1024** | ❌ **完全空白** |

⚠️ 但这一项**受限于硬件**：EP=32 需 2 机、EP=64 需 4 机、EP=1024 需 64 机。
**2-16P 的清单本身就不该覆盖大 EP**，这是设计范围决定的，不是遗漏。

⚠️ 另注：bench 的 `--ep-size` choices 只到 256，
**EP 257~1024 在当前 bench 下不可测**（需改 bench 或直接调 API）。

### 3.5.4 建议补充的 H 高位用例

**优先级高于之前的 topk 补充**，因为 H 的空白跨度是 13.7 倍。

| # | H | tokens | dtype | 目的 |
|---|---|---|---|---|
| G1 | **14336** | 1 | bf16 | 2× 当前最大值 |
| G2 | **28672** | 1 | bf16 | 4× |
| G3 | **49152** | 1 | bf16 | 半程 |
| G4 | **98304** | 1 | bf16 | **官方上限** |
| G5 | **98432** | 1 | bf16 | 上限+128（应失败） |
| G6 | **107008** | 1 | fp8 | **BF16失败/FP8通过的分界** |
| G7 | **109536** | 1 | fp8 | **FP8 上限** |

⚠️ **必须用 `tokens=1`**：H=98304 配 tokens=8192 会占 1.5 GB/rank，
**先撞显存而非 H 上限**，测不出真实边界（详见 2.1 节）。

⚠️ 7 条用例的成本：每条 tokens=1，实际计算量极小，**主要耗时是 Buffer 初始化**。

### 3.5.5 修正之前的错误结论

我此前基于源码分析说"泛化漏掉 topk 32~127"，
现在看**那个缺口相对 H 维度是次要的**：

| 缺口 | 跨度 | 严重度 |
|---|---|---|
| **H 7169~98304** | **13.7 倍** | 🔴 **最高** |
| EP 32~1024 | 32 倍 | 🟡 受硬件限制，可接受 |
| topk 33~128 | 4 倍 | 🟡 官方未声明上限 |

**⇒ 最该补的是 H，不是 topk。**

## 四、9 种异常场景（来自 `DeepEP_CLOS_yichang.txt`）

E1~E6 每条 **V1/V2 各跑一遍**（12 次），E7~E9 仅 V1（3 次），**合计 15 次执行**。

| # | 版本 | 测试场景 | 预期结果 | 优先级 |
|---|---|---|---|---|
| **E1** | V1/V2 | 连续 dispatch 两轮，只 combine 第 2 轮 | 第 2 轮结果算对，之后还能继续下一轮 | 高 |
| **E2** | V1/V2 | 连续 dispatch 两轮，只 combine 第 1 轮；两轮用不同输入、不同路由 | 第 1 轮结果算对；第 2 次 dispatch 没覆盖第 1 轮数据或路由 | 高 |
| **E3** | V1/V2 | 连续 dispatch 两轮，再按 **2 → 1 的顺序** combine | 两轮各自结果都算对 | 高 |
| **E4** | V1/V2 | 一次 dispatch，用**同一 handle** combine 两次，第二次换同布局专家输出 | 两次都成功，各自得到对应结果 | 高 |
| **E5** | V1/V2 | 第 1 轮 dispatch 成功，第 2 轮**所有 rank 上传超容量非法输入**，再 combine 第 1 轮 | 第 2 轮明确报错，**第 1 轮仍能算对**<br>❌ **实测：4/4 组合 device_crash** | 中 |
| **E6** | V1/V2 | 把第 2 轮专家输出配第 1 轮 handle；分行数不同、行数相同两组 | 行数不同应报错；行数相同可能正常返回，**要能发现 token 归错位置**；换回正确 handle 后算对 | 中 |
| **E7** | **V1** | expand 两轮，只 aggregate 第 2 轮 | 第 2 轮结果与单独跑第 2 轮一致 | 中 |
| **E8** | **V1** | expand 两轮，只 aggregate 第 1 轮 | 第 1 轮结果与单独跑第 1 轮一致 | 中 |
| **E9** | **V1** | expand 一次，用**同一 ExpandHandle** 做两次 aggregate，第二次换同布局专家输出 | 两次都成功；第二次结果跟着变 | 中 |

### 覆盖面说明

| 分组 | 场景 | 验证的是什么 |
|---|---|---|
| 多轮 handle 隔离 | E1, E2, E3 | 两轮 dispatch 的 handle / 路由是否互相污染 |
| handle 复用 | E4, E9 | 同一 handle 多次 combine/aggregate 是否幂等 |
| 异常后恢复 | E5 | 前一轮失败是否影响已成功的轮次 |
| handle 错配 | E6 | 用错 handle 时是否报错、能否发现静默错误 |
| V1 特有（expand/aggregate） | E7, E8, E9 | V1 三件套（expand→aggregate）的轮次隔离 |

⚠️ **E6 是最有价值的一条**：它要求"行数相同但内容错配"时**能发现 token 归错位置**。
这类 bug 不会崩溃、不会报错，只会算错——**需要逐 token 比对，不能只看是否抛异常**。

⚠️ **E5 需要注意**：第 2 轮的非法输入要"所有 rank"都上传，
否则单 rank 失败可能被集合通信掩盖。

### 4.1 E5 实测结果：设备级崩溃（2026-11-27）

详见 [`2to16P异常场景结果_20261127.md`](./2to16P异常场景结果_20261127.md)。

**4/4 组合全部 `device_crash`**（EP8/EP16 × V1/V2），非偶发。

| 观测 | 内容 |
|---|---|
| Python 层 | **未拒绝**，直接放行 |
| 实际表现 | 异步 NPU 设备错误：`EE9999 Internal error` / `vector core exception` / `device error type 3, code 507035` |
| 后果 | **整个进程组崩溃**，前序成功的第 1 轮也无法再 combine |

**⇒ 与清单预期「第 2 轮明确报错、第 1 轮仍能算对」不符。**

### 4.2 口径差异必须说明（影响结论性质）

本轮实现用**越界 `topk_idx`**，不是清单字面的**超容量 tokens**：

| | 清单原意 | 本轮实现 |
|---|---|---|
| 非法输入 | tokens 数超 `num_max_tokens_per_rank` | **`topk_idx` 元素值越界**（expert id = `ep×epr`，合法 0..N-1） |
| 触发层 | 算子容量校验（`buffer.py:509`） | **无校验，直达 kernel** |
| 原因 | — | 超容量需重分配 Buffer，OOM 风险不可控 |

**这两者不是同一个测试**：

| 场景 | 测的是什么 | 结果 |
|---|---|---|
| 超容量 tokens | 算子的**容量校验是否生效** | 未执行 |
| 越界 expert id | **输入合法性校验缺失** | ✅ 已发现崩溃 |

### 4.3 崩溃根因已在源码层定位（我核实）

查两版源码，**都只校验 topk 的"宽度"，不校验"取值"**：

```python
# elastic_v2.py:607  —— 只查 num_topk 这个数，不查 topk_idx 里的值
if num_topk > num_experts:
    raise ValueError("num_topk must not exceed num_experts")

# buffer_v1.py     —— 搜不到任何 topk_idx 取值范围校验
```

**⇒ 这是真实的输入校验缺口**：`topk_idx` 里出现 ≥ `num_experts` 的值时，
Python 层放行，kernel 收到越界 expert id 后 vector core exception。

**这条比清单原本想测的"容量校验"更有价值**——它是真正的健壮性缺陷，
而不是"预期内的拒绝行为"。

⚠️ 但仍建议补跑真正的**超容量 tokens** 场景，两者是不同维度：
- 越界 expert id → 已验证会崩
- 超容量 tokens → 应报 `local token count exceeds`，**未验证**

## 五、执行方式建议

| 批次 | 内容 | 条数 | 说明 |
|---|---|---|---|
| 批次 1 | 泛化精度（`精度用例清单_2to16P.md`） | 200 | 2/4/8/16P 各 50 |
| 批次 2 | 形状边界 S1~S8 × 4 EP | 32 | 含 3 条预期被拒 |
| 批次 3 | 专家边界 X1~X8 × 4 EP | 32 | 含 2 条预期报错 |
| 批次 4 | 异常场景 E1~E9 | 9 逻辑场景 | E1~E6×2 + E7~E9×1 = **15 次** |

**建议顺序**：批次 2 → 3 → 1 → 4。

理由：边界先跑能快速暴露形状/参数问题；泛化 200 条耗时最长放中间；
异常场景需要写专门的编排逻辑，放最后。
