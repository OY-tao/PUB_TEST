## 一、边界来源核实：三个不同的"边界"，不能混用

⚠️ **2026-11-27 修正**：初版边界表把**库文档**的推荐值当成了**算子校验**，
已回源码逐条核实。三者不一致，必须分清在哪一层生效。

### 1.1 三个来源的区别

| 来源 | 是什么 | 在哪生效 | 能否作判据 |
|---|---|---|---|
| **库文档**（`docs/elastic.md` 等） | 官方声明的支持范围 | 无强制力 | ❌ 只作参考 |
| **bench 参数校验**（`bench_v2_bandwidth.py:137-141`） | 基准脚本的入参检查 | 参数解析阶段 | ✅ 但只管 bench 能跑什么 |
| **算子源码校验** | 真正的 API 契约 | dispatch/combine 调用时 | ✅ **真正的算子边界** |

### 1.2 逐项核实结果

| 项 | **算子源码真实校验**（核实自源码） | 库文档 | 我初版写的 |
|---|---|---|---|
| `hidden` 上界 | **无上界**。V2 只查 `hidden > 0`（`elastic.py:230`） | 7168 | ❌ 7168 |
| `hidden` 对齐 | V2 **无 %128 强制**；`x hidden size` 只与 Buffer 构造值比对（`elastic.py:1380`） | BF16 16 / FP8 128 | ❌ 写成硬约束 |
| `num_topk` 上界 | **V2: `_MAX_TOPK = 128`**（`elastic.py:45,415`）；V1 未见显式校验 | V1 16 / V2 32 | ❌ 16 / 32 |
| `num_tokens` 上界 | **无上界**。只查 `> 0` 且 `≤ num_max_tokens_per_rank`（`buffer.py:110,509`） | 16384 | ❌ 16384 |
| 专家数 `E` | **无显式上界**。V2 要求 `num_experts % world_size == 0`（`elastic.py`） | ≤1024 | ❌ ≤1024 |
| `num_experts` 上限 | `_MAX_LOCAL_EXPERTS_FOR_SIZE_HINT = 1024` —— **仅用于 size hint 估算，不是校验** | 1024 | ❌ 当成硬约束 |
| 节点内 rank | `_MAX_SHMEM_INTRANODE_RANKS = 1024` —— **是 rank 数，不是专家数** | — | 初版完全没提 |
| `num_aiv` 上界 | `_MAX_NUM_AIV`：**架构 3510 → 64，2201 → 48**（`config.py:22-27`） | — | 我按 64 写 |

### 1.3 三条必须改正的误解

**误解 1：hidden ≤ 7168 是算子限制**

错。7168 是**文档推荐上限**，源码只查 `hidden > 0`。
真正的限制来自 **bench 参数层**（`hidden % 128`）和 kernel 内部 workspace 预算。

**误解 2：`1024` 是专家数上限**

错。源码里两处 1024 都不是专家数校验：

```python
_MAX_SHMEM_INTRANODE_RANKS     = 1024   # 节点内 rank 数上限
_MAX_LOCAL_EXPERTS_FOR_SIZE_HINT = 1024   # size hint 估算用的上界，仅影响 workspace 预估
```

**误解 3：topk ≤ 32**

错。V2 的真实上限是 **`_MAX_TOPK = 128`**（`elastic.py:45`）。
32 是**文档**的说法；bench 参数层用的是 `min(128, ep×epr)`。
⇒ 三处口径：文档 32、源码 128、bench `min(128, ep×epr)`。

### 1.4 那"边界测试"到底该测什么

既然源码没有形状上界校验，**真正的边界就不在参数层，而在以下几处**：

| 真实边界类型 | 位置 | 怎么测 |
|---|---|---|
| **workspace / 显存预算** | kernel 内部，`get_buffer_size_hint` | 逐级放大 hidden/tokens 直到构造失败 |
| **bench 参数层** | `bench_v2_bandwidth.py:137-141` | `hidden % 128`、`topk ≤ min(128, ep×epr)` |
| **V2 整除契约** | `elastic.py` | `num_experts % world_size != 0` 应报错 |
| **topk 真上限** | `_MAX_TOPK = 128` | topk=129 应报错，topk=128 应通过 |
| **token 容量** | `num_max_tokens_per_rank` | 超容量应报 `local token count exceeds...` |
| **路由采样** | `route_workloads.generate` | `k > ep×epr` 时 Python 抛 `ValueError` |

⚠️ **结论：初版的 S1~S8 里，只有 S1（tokens=1）、S4（FP8 hidden=128）、S5（hidden=7168）
算"有意义的边界"，其余几条要么在参数层就被拦、要么根本不是算子边界。**

### 1.5 已修正的用例设计原则

新原则：**每条边界用例必须写明"在哪一层验证"和"预期错在哪一层"**。

| 用例 | 验证层 | 判据 |
|---|---|---|
| hidden=7168 | kernel 预算 | 正常出结果 |
| hidden=7169 | bench 参数层 | `hidden % 128` 不过 → p.error |
| hidden=8192 | kernel 预算 | `8192%128==0` 能过 bench，**看 kernel 是否 OOM** |
| topk=128 | 算子 `_MAX_TOPK` | 应通过 |
| topk=129 | 算子 `_MAX_TOPK` | 应报 `num_topk must not exceed 128` |
| experts=3 (EP2) | V2 整除契约 | `3 % 2 != 0` → 应报错 |
| tokens 超容量 | `num_max_tokens_per_rank` | 应报 `local token count exceeds` |

## 三、专家边界用例（每个 EP 8 条，已按源码重设）

**源码事实**：V2 的 `_MAX_TOPK = 128`；`num_experts` 无显式上界，
但要求 `num_experts % world_size == 0`；V1 未见 topk / experts 的显式校验。

| # | E（全局） | epr | topk | 验证层 | 预期 |
|---|---|---|---|---|---|
| X1 | **P**（epr=1） | 1 | **1** | kernel | 正常（每卡 1 专家，最小 E） |
| X2 | P | 1 | 2 | kernel | 正常（topk>epr，跨卡路由） |
| X3 | **1024** | 1024/P | 8 | kernel 预算 | 正常（文档推荐上限） |
| X4 | 1024 | 1024/P | **128** | **算子 `_MAX_TOPK`** | **正常**（真上限边界） |
| X5 | 1024 | 1024/P | **129** | **bench 参数层先拦** | `129 > min(128,1024)` → **p.error**，到不了算子层 |
| X6 | P | 1 | **P+1** | bench 参数层 | `topk > min(128, P)` → p.error |
| X7 | **epr 极大** | **1024/P ×2** | 8 | kernel 预算 | E 超文档 1024，**看 kernel/workspace 实际是否拒绝**（见下方说明） |
| X8 | 1024 | 1024/P | 1 | kernel | 正常（topk 下界） |

⚠️ **X3/X4/X5/X8 的 epr**：`epr = 1024 / EP`，EP2→512、EP4→256、EP8→128、EP16→64，均为整数。

⚠️ **相比初版的改动**：

| 原用例 | 问题 | 改成 |
|---|---|---|
| X4 topk=16 | 16 是**文档**的 V1 上限，不是源码校验 | topk=**128**（`_MAX_TOPK` 真上限） |
| X5 topk=32 | 32 是文档值，源码是 128，**32 根本不会报错** | topk=**129**（越 `_MAX_TOPK` 一格） |
| X7 E=1025 | **无 `E≤1024` 校验**，epr 还非整数，拒绝点不明 | **奇数 E**（触发真正的整除契约） |

⚠️ **X7 的一个坑（我核实后发现自己也设计错了）**：

原本想用「奇数 E」触发 `num_experts must be divisible by world_size`，
但 **`E = ep × epr` 在 ep 为偶数（2/4/8/16）时恒为偶数**，
且 `(ep×epr) % ep ≡ 0` **恒成立** ⇒ **这个契约在本测试的 EP 下永远满足，构造不出违反**。

所以 X7 改成「epr 极大」去探 E 超文档上限 1024 时 kernel 的真实行为。
若要真正测整除契约，必须用 **EP=3 或 5 这类奇素数 EP**（但 bench 的
`--ep-size` choices 只允许 2/4/8/16/32/64/128/256，**做不到**）。
⇒ **该契约在本 bench 下不可测**，已登记为已知盲区。

**参数模板**：

```
--ep-size=<EP> --experts-per-rank=<epr> --num-topk=<k> --num-tokens=1024 --hidden=2048
```

⚠️ **X5 也测不到算子层（核实后确认）**：

`bench_v2_bandwidth.py:140` 的 `num_topk > min(128, ep×epr)` 在**参数解析阶段**就 p.error，
所以 topk=129 **永远到不了** `elastic.py` 的 `_MAX_TOPK = 128` 校验。

| | bench 参数层 | 算子层 `_MAX_TOPK` |
|---|---|---|
| 检查 | `topk > min(128, ep×epr)` | `topk > 128` |
| 生效时机 | 参数解析 | dispatch 调用 |
| topk=129 时 | **先拦住** | 到不了 |

⇒ **算子层的 `_MAX_TOPK` 校验在本 bench 下不可达**（bench 更严格）。
这与 1.5 节的结论一致：**bench 参数层是比算子更早的一道闸**。

⚠️ **X5 / X6 / X7 都是预期报错的用例**，判据需采集 stderr（见第六章）。

### 3.5 不可测的边界（已知盲区）

核实源码后发现，以下几类"边界"**在本 bench 下无法验证**：

| # | 想测的边界 | 为什么测不到 |
|---|---|---|
| 1 | 算子 `_MAX_TOPK = 128` | bench 参数层 `min(128, ep×epr)` **更严格且更早**，129 被它拦住 |
| 2 | `num_experts % world_size != 0` | `E = ep×epr` 且 bench 的 ep 只允许 2/4/8/16/32/64/128/256，**全为偶数** ⇒ 恒满足 |
| 3 | `hidden ≤ 7168` | 源码**无此校验**，只有 size hint 估算；且 bench 要求 `%128`，两者都非"7168 硬限" |
| 4 | `tokens ≤ 16384` | 源码**无此校验**，只查 `>0` 与 `≤num_max_tokens_per_rank` |
| 5 | `_MAX_SHMEM_INTRANODE_RANKS = 1024` | 这是**节点内 rank 数**，本 bench 每节点 ≤16，**结构上碰不到** |
| 6 | 奇素数 EP 的整除契约 | `--ep-size` choices 无 3/5/7，**无法构造** |

⚠️ **这意味着"边界测试"的真实覆盖面比预想窄**。
真正可测的边界只有：

| 可测 | 验证层 |
|---|---|
| tokens=1（下界） | kernel |
| tokens 超 `num_max_tokens_per_rank` | 算子 `buffer.py:509` |
| hidden `%128 != 0` | bench 参数层 |
| hidden 极大导致 OOM | kernel 预算 |
| topk > `min(128, ep×epr)` | bench 参数层 |
| E 极大导致 OOM | kernel 预算 |
| FP8 hidden=128（最小量化块） | kernel |

**⇒ 若确实要验证算子自身的契约（`_MAX_TOPK`、整除、hidden 上限），
需要绕过 bench 直接调用 `Buffer.dispatch` —— 那是另一套测试脚本，不在本清单范围。**

## 三·五、泛化精度用例对边界的覆盖情况（实测核查）

**问题**：边界用例若因 bench 参数层拦截而测不到算子，泛化用例又不覆盖，
该边界就**等于没测**。下面逐条核对 200 条泛化用例的实际覆盖。

### 3.5.1 覆盖结果：16 个边界点，覆盖 8 个

| 边界 | 条件 | 泛化覆盖 |
|---|---|---|
| S1 | tokens=1 | ✅ **24 条** |
| S2 | tokens=16384 | ✅ **24 条** |
| S3 | tokens 超容量 | ❌ **0 条** |
| S4 | hidden=128（FP8 下界） | ✅ 4 条 |
| S5 | hidden=7168（文档上限） | ✅ **28 条** |
| S6 | hidden 非 128 对齐 | ❌ 0 条 |
| S7 | hidden=8192 | ❌ 0 条 |
| S8 | hidden=16384 | ❌ 0 条 |
| X1 | epr=1（E=P） | ✅ 8 条 |
| X2 | epr=1 且 topk=2 | ✅ 4 条 |
| X3 | E=1024 | ✅ 3 条 |
| X4 | **topk=128** | ❌ **0 条** |
| X5 | topk=129 | ❌ 0 条 |
| X6 | topk=P+1 越界 | ❌ 0 条 |
| X7 | E>1024 | ❌ 0 条 |
| X8 | topk=1 | ✅ 8 条 |

**覆盖率：8/16 = 50%**

### 3.5.2 缺口分类：哪些是真缺口，哪些不是

| 类型 | 缺口 | 该不该由泛化补 |
|---|---|---|
| **真缺口（高）** | **X4 topk=128** | ✅ **应该**。真上限不测=没验证 topk 边界 |
| **真缺口（高）** | **S3 tokens 超容量** | ⚠️ 不该。这是**负向用例**，泛化应全为正向 |
| 探测类（中） | S7 hidden=8192、S8 hidden=16384 | ❌ 不该。属"探 OOM 点"，泛化里放会中断整批 |
| 负向类（中） | S6、X5、X6 | ❌ 不该。负向用例不能混进正向泛化 |
| 低价值 | X7 E>1024 | ❌ 不该。E 无真实上界 |

**⇒ 只有 X4（topk=128）是真正应当由泛化用例覆盖却漏掉的。**

### 3.5.3 最严重的发现：topk 32~127 完全空白

| 项 | 值 |
|---|---|
| 泛化用例实际用到的 topk | `[1, 2, 4, 8, 16, 32]` |
| 算子真实上限 `_MAX_TOPK` | **128** |
| **空白区间** | **32 ~ 127，共 96 个值，0 条用例** |

**这是本次核查最值得关注的一条**：

- 文档说 V2 topk 上限 32 → 我按 32 设计
- 源码 `_MAX_TOPK = 128` → 实际支持到 128
- **⇒ 32 以上从未被测试过**

如果 kernel 在 topk>32 时有正确性问题（如 workspace 不足、索引越界），
**当前 200 条泛化 + 16 条边界全都发现不了**。

### 3.5.4 建议补充的用例（不改现有 200 条，另加）

| 用例 | topk | hidden | 目的 |
|---|---|---|---|
| N1 | **48** | 2048 | 跨过文档上限 32，验证是否正常 |
| N2 | **64** | 2048 | 中段 |
| N3 | **96** | 2048 | 接近上限 |
| N4 | **128** | 2048 | **真上限边界** |
| N5 | 128 | 7168 | 上限 topk + 上限 hidden 组合 |
| N6 | 128 | 128 | 上限 topk + 最小 hidden（最省资源） |

⚠️ N1~N6 的 `ep × epr` 必须 ≥ topk，建议用 `EP=16, epr=32 → 512`，
这样 `min(128, 512) = 128`，bench 参数层放行（已逐条验算，6 条全部通过）。

⚠️ **待验证**：`route_workloads.generate` 用 `rng.sample(range(experts), k)`，
要求 `k ≤ experts`。E=512 ≥ 128 满足，但**本地无 torch 无法实跑确认**，
首次执行时请先跑 N1（topk=48）确认路由生成正常。

**另需 1 条负向**：`topk=129`（预期 bench p.error），单独放边界批次，不混进泛化。

### 3.5.5 结论

**泛化用例覆盖了 8/16 个边界点，但漏掉了最重要的一个：topk 真上限 128。**

原因是我按文档的 32 设计，而源码是 128。
**这不是"边界用例没覆盖"的问题，是"泛化用例的参数范围本身就不够"。**

建议单独加 6 条 topk 高位用例（3.5.4），成本很低、价值明确。

## 四、9 种异常场景（来自 `DeepEP_CLOS_yichang.txt`）

E1~E6 每条 **V1/V2 各跑一遍**（12 次），E7~E9 仅 V1（3 次），**合计 15 次执行**。

| # | 版本 | 测试场景 | 预期结果 | 优先级 |
|---|---|---|---|---|
| **E1** | V1/V2 | 连续 dispatch 两轮，只 combine 第 2 轮 | 第 2 轮结果算对，之后还能继续下一轮 | 高 |
| **E2** | V1/V2 | 连续 dispatch 两轮，只 combine 第 1 轮；两轮用不同输入、不同路由 | 第 1 轮结果算对；第 2 次 dispatch 没覆盖第 1 轮数据或路由 | 高 |
| **E3** | V1/V2 | 连续 dispatch 两轮，再按 **2 → 1 的顺序** combine | 两轮各自结果都算对 | 高 |
| **E4** | V1/V2 | 一次 dispatch，用**同一 handle** combine 两次，第二次换同布局专家输出 | 两次都成功，各自得到对应结果 | 高 |
| **E5** | V1/V2 | 第 1 轮 dispatch 成功，第 2 轮**所有 rank 上传超容量非法输入**，再 combine 第 1 轮 | 第 2 轮明确报错，**第 1 轮仍能算对** | 中 |
| **E6** | V1/V2 | 把第 2 轮专家输出配第 1 轮 handle；分行数不同、行数相同两组 | 行数不同应报错；行数相同可能正常返回，**要能发现 token 归错位置**；换回正确 handle 后算对 | 中 |
| **E7** | **V1** | expand 两轮，只 aggregate 第 2 轮 | 第 2 轮结果与单独跑第 2 轮一致 | 中 |
| **E8** | **V1** | expand 两轮，只 aggregate 第 1 轮 | 第 1 轮结果与单独跑第 1 轮一致 | 中 |
| **E9** | **V1** | expand 一次，用**同一 ExpandHandle** 做两次 aggregate，第二次换同布局专家输出 | 两次都成功；第二次结果跟着变 | 中 |

### 覆盖面说明

| 分组 | 场景 | 验证的是什么 |
|---|---|---|
| 多轮 handle 隔离 | E1, E2, E3 | 两轮 dispatch 的 handle / 路由是否互相污染 |
| handle 复用 | E4, E9 | 同一 handle 多次 combine/aggregate 是否幂等 |
| 异常后恢复 | E5 | 前一轮失败是否影响已成功的轮次 |
| handle 错配 | E6 | 用错 handle 时是否报错、能否发现静默错误 |
| V1 特有（expand/aggregate） | E7, E8, E9 | V1 三件套（expand→aggregate）的轮次隔离 |

⚠️ **E6 是最有价值的一条**：它要求"行数相同但内容错配"时**能发现 token 归错位置**。
这类 bug 不会崩溃、不会报错，只会算错——**需要逐 token 比对，不能只看是否抛异常**。

⚠️ **E5 需要注意**：第 2 轮的非法输入要"所有 rank"都上传，
否则单 rank 失败可能被集合通信掩盖。

## 五、执行方式建议

| 批次 | 内容 | 条数 | 说明 |
|---|---|---|---|
| 批次 1 | 泛化精度（`精度用例清单_2to16P.md`） | 200 | 2/4/8/16P 各 50 |
| 批次 2 | 形状边界 S1~S8 × 4 EP | 32 | 含 3 条预期被拒 |
| 批次 3 | 专家边界 X1~X8 × 4 EP | 32 | 含 2 条预期报错 |
| 批次 4 | 异常场景 E1~E9 | 9 逻辑场景 | E1~E6×2 + E7~E9×1 = **15 次** |

**建议顺序**：批次 2 → 3 → 1 → 4。

理由：边界先跑能快速暴露形状/参数问题；泛化 200 条耗时最长放中间；
异常场景需要写专门的编排逻辑，放最后。

## 六、编译执行命令模板

单个用例（单机，EP≤16）：

```bash
python benchmarks/clos/bench_v2_precision.py \
    --precision-only \
    --ep-size=8 --nnodes=1 \
    --num-tokens=1024 --hidden=2048 --num-topk=8 --experts-per-rank=32 \
    --dtypes=bf16 --expand=0 --aiv=32 \
    --run-id=prec_ep8_001 \
    --output=/tmp/precision_out
```

⚠️ **`--precision-only` 只存在于设备上的 `bench_*_precision.py`**，
上游的 `bench_v1_bandwidth.py` / `bench_v2_bandwidth.py` **没有这个参数**。
需确认设备上这两个文件的 sha256 与上次一致（见 `run_ep64_precision.py` 里的 `PRECISION_SHA`）。
