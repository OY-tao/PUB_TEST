## ⚠️ 跑测前必做：核对走的是 `global_clos`

**开工前第一件事，确认导入路径没被改动。** 一旦有人把 import 换回 `direct`
或换成 `mesh_clos`，测的就不是同一套实现了，全部数据作废。

```bash
# 两处必须都是 global_clos
grep -n "from deep_ep.backends" benchmarks/clos/bench_v1_bandwidth.py
grep -n "from deep_ep.backends" benchmarks/clos/bench_v2_bandwidth.py
```

期望输出（行号可能漂移，模块名必须一致）：

```
bench_v1_bandwidth.py:102:    from deep_ep.backends.global_clos import Buffer
bench_v1_bandwidth.py:104:    from deep_ep.backends.direct import Config      ← Config 例外，正常
bench_v2_bandwidth.py:387:    from deep_ep.backends.global_clos import ElasticBuffer
bench_v2_bandwidth.py:250:    from deep_ep.backends import direct as clos     ← 仅校验 so 哈希，正常
```

**判据**：`Buffer` 与 `ElasticBuffer` 必须来自 `global_clos`。
`Config` 来自 `direct`、`direct as clos` 出现在 `loaded_identity()` 里，**都属正常**，
不要误判（详见「零」章的 import 作用表）。

更可靠的运行时核对（在设备上、跑第一个 case 之前执行）：

```bash
python -c "
from deep_ep.backends.global_clos import Buffer, ElasticBuffer
from deep_ep.backends.direct.api import Buffer as ApiBuffer
from deep_ep.backends.direct.buffer import Buffer as DirectBuffer
print('global_clos.Buffer  ->', Buffer.__module__)
print('api.Buffer          ->', ApiBuffer.__module__)
print('direct.buffer.Buffer->', DirectBuffer.__module__)
print('是同一对象:', Buffer is ApiBuffer)
print('是子类关系:', issubclass(ApiBuffer, DirectBuffer))
"
```

**期望**：`Buffer is ApiBuffer` 为 **True**，`issubclass(ApiBuffer, DirectBuffer)` 为 **True**。
若 `Buffer.__module__` 出现 `mesh_clos`，说明走错实现，**立即停止**。

**最省事的一行判据**（贴到脚本或 CI 里当断言）：

```bash
python -c "import sys; from deep_ep.backends.global_clos import Buffer, ElasticBuffer; bad=[c.__name__ for c in (Buffer,ElasticBuffer) if 'mesh_clos' in c.__module__]; print('FAIL: 走了 mesh_clos', bad) if bad else print('OK: global_clos'); sys.exit(1 if bad else 0)"
```

**为什么这条值得单列**：`mesh_clos` 有独立实现（`elastic.py` 78 KB，与 `direct` 的 64 KB
是两套代码），一旦走错，性能数字和精度结论**都不能与 `direct` 的结果对比**——
这属于比 case 配比错误更严重的低级事故，且从结果上看不出来，只能靠事前核对。

## 零、被测对象确认

### 只有这两个脚本被纳入本设计

| 脚本 | 角色 | 是否被测 |
|---|---|---|
| `benchmarks/clos/bench_v1_bandwidth.py` | V1 主脚本 | ✅ |
| `benchmarks/clos/bench_v2_bandwidth.py` | V2 主脚本，**同时是 V1 的依赖** | ✅ |
| `benchmarks/clos/bench_fast_sweep.py` | 只测性能、**不做数值验证**的快速扫描工具 | ❌ **不在本设计范围** |
| `benchmarks/bench_ep.py` | 上游通用入口，非 CLOS 专用 | ❌ 不涉及 |
| `benchmarks/clos/bandwidth_multinode.py` | 多机编排辅助模块，被上面两个 import | 依赖，非被测 |

### 两个主脚本的关系

**`bench_v1_bandwidth.py` 不是独立实现**，它 `import bench_v2_bandwidth as shared`：

```python
# bench_v1_bandwidth.py 复用 V2 的：
#   参数解析、多机编排 launch()、路由生成 route_workloads、
#   字节账本 stage_metrics.byte_ledger、profiler 解析
# 只有 V1Operations 类和 worker() 的调用方式不同
```

⇒ **改 V2 的参数/编排/账本，V1 自动跟着变**；改 V1 的测量语义不影响 V2。

### 为什么排除 `bench_fast_sweep.py`

它的 docstring 首行原文：

> *"One SHMEM initialization, existing full-Clos peer schedules, **performance only**."*

> *"**No numerical validation is performed**; every report explicitly records that."*

三条硬差异：

| 维度 | 本设计用的两个脚本 | bench_fast_sweep.py |
|---|---|---|
| 精度校验 | ✅ profiling 之前先校验 | ❌ **完全不做** |
| 每个配置的进程组 | 独立 torchrun（fresh group） | 一次 SHMEM 初始化跑完 |
| 形状 | 参数化任意形状 | 硬编码 `SHAPES = ((8192,2816,8,32), (16384,7168,6,64))` |

**结论**：`bench_fast_sweep.py` 适合快速摸性能上限，但**没有精度校验、形状不可泛化**，
不满足本设计「11 项中的 4 个性能项必须同时拿到精度结论」的要求，故不采用。

### 算子实现路径：`global_clos` → `api` → `buffer/elastic`

**bench 两处都是 `from deep_ep.backends.global_clos import ...`，不是 `direct`。**
这条链路必须确认，否则测的可能不是同一个实现。

```
bench_v1_bandwidth.py:102   from deep_ep.backends.global_clos import Buffer
bench_v2_bandwidth.py:387   from deep_ep.backends.global_clos import ElasticBuffer
```

调用链：

```
deep_ep.backends.global_clos          ← bench 实际 import 的
  __init__.py:  from ..direct import api
                Buffer = api.Buffer
                ElasticBuffer = api.ElasticBuffer
        ↓
deep_ep.backends.direct.api           ← 兼容层
  class Buffer(SourceBuffer)          ← 子类，加参数名别名
  class ElasticBuffer(SourceElasticBuffer)
        ↓
deep_ep.backends.direct.buffer        ← V1 真正实现（58,037 B）
deep_ep.backends.direct.elastic       ← V2 真正实现（64,318 B）
```

**注意别和 `mesh_clos` 混淆**——后者有独立实现，`global_clos` 没有：

| 目录 | 文件构成 | 是否独立实现 |
|---|---|---|
| `backends/global_clos/` | 仅 `__init__.py`（274 B） | ❌ 别名，指向 `direct` |
| `backends/mesh_clos/` | `buffer.py`(9 KB) + `elastic.py`(78 KB) + `_elastic_layout.py`(7.8 KB) | ✅ 独立实现 |
| `backends/direct/` | `buffer.py`(58 KB) + `elastic.py`(64 KB) + 12 个模块 | ✅ 独立实现，**本设计实际测的是这份** |
| `backends/mesh_pcie/` | 仅 `__init__.py`(2.6 KB) | 另议 |

本设计测的是 `direct` 那套。`mesh_clos` 是 MTE 路径的实现，不在本次范围。

**三个关键事实**：

1. **`global_clos` 只是个入口别名**，目录下只有 274 B 的 `__init__.py`，没有独立实现。
   docstring 原文：*"Global Clos topology entry; the machine selector fixes UDMA transport."*

2. **`api.Buffer` 是 `buffer.Buffer` 的子类**，差异只在参数名兼容：
   ```python
   class Buffer(SourceBuffer):
       __init__ = keyword_aliases(SourceBuffer.__init__, {
           "num_scaleup_bytes": "num_nvl_bytes",      # 上游 NV 命名 → Ascend 命名
           "num_scaleout_bytes": "num_rdma_bytes",
           "allow_memory_transport_for_low_latency_mode": "allow_nvlink_for_low_latency_mode",
           "allow_multinode_memory_transport": "allow_mnnvl",
       })
       dispatch = keyword_aliases(SourceBuffer.dispatch,
                                  {"num_tokens_per_scaleout_rank": "num_tokens_per_rdma_rank"})
   ```
   **测量逻辑、kernel、阶段解析全在父类里**，子类不改变行为。

3. **`Config` 仍从 `direct` 取**（`bench_v1:104`），因为 `global_clos` 的
   `__all__` 只导出 `Buffer`/`ElasticBuffer`/`buffer_class`，**不含 Config**。

### 另两处 import 的作用（不是被测对象）

| 位置 | 内容 | 作用 |
|---|---|---|
| `bench_v2:250` | `from deep_ep.backends import direct as clos` | 仅用于 `loaded_identity()` 读 `/proc/self/maps` **校验加载的 .so 哈希**，不实例化任何对象 |
| `bench_v2:1140` / `bench_v1:103` | `from deep_ep import topk_idx_t` | 取 `topk_idx` 的 dtype（编译期决定 int32/int64） |

### 对用例设计的影响

**无影响**，但有三点必须记住：

- 报缺陷时**指向 `direct/buffer.py` 与 `direct/elastic.py` 的行号**，因为实现在这两个文件
- 不要写成 `global_clos.buffer`——**这个模块不存在**，会误导排查
- `api` 子类的参数别名意味着**上游 NV 风格的参数名也能传**（如 `num_scaleup_bytes`），
  但本设计统一用 Ascend 命名（`num_nvl_bytes`），避免歧义

### 3.2 A 形状（700）

| 维度 | 取值 | 数量 | 说明 |
|---|---|---|---|
| `tokens` | 1-65536 | **25 档** | 见下方档位表 |
| `hidden` | 512-16384 | **7 档** | 全为 128 的倍数 |
| `dtype` | bf16, fp8 | 2 档 | |
| `expand` | 0, 1 | 2 档 | |

`25 × 7 × 2 × 2 = 700`

**tokens 的 25 档**（按几何级数加密采样）：

```
1, 64, 128, 256, 512, 768, 1024, 1536, 2048, 3072, 4096, 5120, 6144,
7168, 8192, 10240, 12288, 14336, 16384, 20480, 24576, 28672, 32768,
49152, 65536
```

- 小端密集（1~4096 共 11 档）：捕捉 `layout_us` 占比、小包效率
- 中段对齐真实模型（6144 / 7168 / 8192）：对齐 Llama / Mixtral 配置
- 大端稀疏（16384~65536 共 7 档）：看带宽饱和与容量上限

**hidden 的 7 档**：512, 1024, 2048, 4096, **6144**, 8192, 16384

其他固定：`ep=8`、`topk=8`、`experts_per_rank=32`、`aiv=32`、`route=uniform`。

⚠️ **expand=1 的两个约束**：
- `tokens≥32768` 或 `hidden≥8192` 的 case 要多占 0.7~2.2 GB HBM，先确认工作区够
- expand=1 走 expert-major 布局，数值与非 expanded 不可比，精度判定分组

⚠️ **A 组是 1148 例的主要耗时来源**：按大形状单 case 约 26 秒估，A 组约 5 小时，
占总时长七成以上。若需缩短，优先削 `hidden=16384` 那 100 例。

### 3.4 C 路由（120）

固定 `ep=8`、`tokens=8192`、`hidden=6144`、`topk=8`。**每项均按 2 dtype × 2 expand = 4 种组合展开。**

| 路由配置         | 组数                       | × 组合 | 例数      |
| ------------ | ------------------------ | ---- | ------- |
| uniform      | 2                        | × 4  | 8       |
| rank_hotspot | 6 skew × 3 hotspot = 18  | × 4  | 72      |
| local_group  | 2 group × 3 fraction = 6 | × 4  | 24      |
| mask         | 4 rate                   | × 4  | 16      |
| **小计**       |                          |      | **120** |

#### 3.5.1 32P 双机实测配置

**环境**：`30.104.128.4`（node 0）、`30.104.128.6`（node 1），各 16 卡。

**参数约束（bench 校验，不满足直接 p.error）**：

```python
local_world_size = ep_size // nnodes          # 必须 1..16
ep_size % nnodes == 0                          # 必须整除
node_rank < nnodes
master-addr 不能是 localhost/0.0.0.0/::1/127.* # 必须可达
run_id 两机必须相同，格式 [A-Za-z0-9_-]{1,64}
```

32P 的合法解只有 **`nnodes=2`（每节点 16 卡，正好是上限）**：

| nnodes | 每节点卡数 | 是否可行 |
|---|---|---|
| 1 | 32 | ❌ 超 16 上限 |
| **2** | **16** | ✅ **唯一可行** |
| 4 | 8 | ✅ 但需 4 机，本次只有 2 台 |
| 8 | 4 | ✅ 需 8 机 |

**两机执行命令**（必须同时启动，run-id 一致）：

```bash
# node 0 (30.104.128.4)
python benchmarks/clos/bench_v2_bandwidth.py \
    --ep-size=32 --nnodes=2 --node-rank=0 \
    --master-addr=30.104.128.4 --master-port=29500 \
    --run-id=clos32p_v2 \
    --num-tokens=8192 --hidden=6144 --num-topk=8 --experts-per-rank=32 \
    --dtypes=bf16 fp8 --expand=0 1 --aiv=32 \
    --output=/tmp/run_32p

# node 1 (30.104.128.6) —— 只改 node-rank 和 first-device
python benchmarks/clos/bench_v2_bandwidth.py \
    --ep-size=32 --nnodes=2 --node-rank=1 \
    --master-addr=30.104.128.4 --master-port=29500 \
    --run-id=clos32p_v2 \
    --num-tokens=8192 --hidden=6144 --num-topk=8 --experts-per-rank=32 \
    --dtypes=bf16 fp8 --expand=0 1 --aiv=32 \
    --output=/tmp/run_32p
```

**执行注意**：

| 项 | 说明 |
|---|---|
| `--master-port` | 默认 29500，**bench 会占用 master-port+1**，所以两端口都要通 |
| `--first-device` | 每节点起始物理卡，默认 0；两机卡号布局须一致 |
| `--output` | 每节点写各自本地路径，最后汇总时合并 |
| `run-id` | 两机必须完全相同，否则 rendezvous 失败 |
| 启动时序 | 两机必须**同时进入**，先启动的一方会等第二个 |
| 超时 | `--rendezvous-timeout`（默认 300s）、`--collection-timeout`（默认 600s） |

**本组在 1148 例中的位置**：`D 拓扑` 的 `EP=32, nnodes=2` 那 2 例（bf16/fp8 各一）。
若只想跑这 2 例而不跑 D 组其余 26 例：


数据看着正常但对不上，且极难定位。跑前必须两边 `git rev-parse HEAD` 对比。

⚠️ **第 7 项要注意 bench 占两个端口**：`master-addr` 用 `master-port`（默认 29500），
torchrun 内部再占 `master-port + 1`（29501）。只放通 29500 会在 init 阶段卡住。

### 只采精度，不采性能

- 使用现有 `bench_v1_precision.py` / `bench_v2_precision.py`，**每次调用及所有 worker 都带 `--precision-only`**；精度断言、fresh/cached、combine 校验和销毁检查保留。

- `SHMEM_UDMA_CONNECT_TIMEOUT_MS=300000` 注入四节点及所有 worker。
- G 中 iterations/warmup 等仅保留参数兼容性；精度模式不验证原“带宽口径”目标。H 仅重复正确性，不声称完成性能稳定性验证；L7 独立32例不包括在此脚本。
- 大tokens/hidden/topk/epr和1GiB huge-pages共 **352条适用调用/API** 标为资源审核；默认执行会拒绝这些选择。审核CPU golden与HBM/huge-pages资源后，才可显式 `--allow-large`；静态参数适用不代表资源保证。
