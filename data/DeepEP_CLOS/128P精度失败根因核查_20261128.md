# 128P 精度失败根因核查：成功任务 deep_ep 实际解析路径（2026-11-28）

> **性质**：纯静态核查，只读源码 / 产物 / 日志。未跑测试、未部署、未改脚本、未动设备。
> **结论**：此前几轮的「`shmem_ip_port` / UDMA 构造参数 / 进程组类型」假设**都不是根因**。
> 根因是 **128P 精度 worker 与今早成功任务加载了两套不同代码的 `deep_ep`**（版本号都报
> `0.1.0.dev5`，但 `buffer.py` 字节不同），且成功任务依赖的 `DEEPEP_CLOS_QP_PLANS` 约束
> 在精度任务里既没设置、加载的旧版也根本不读它。

## 1. 核查问题

同一 8 机容器、同样 128 rank（`--nnodes 8 --nproc_per_node 16`）：
今早 `full_matrix.py`（`ep128_retest_20261128_091417`，`run.exit=0`）成功；
128P 精度 smoke 连续 15 次 attempt 全失败，均在首个 `Buffer` 构造处
`aclshmemx_init_attr ... status=-7`。必须确定成功任务运行时 `import deep_ep` 解析到哪里。

## 2. 硬证据

### 2.1 成功任务自己记录的模块路径

`ep128_retest_20261128_091417/ep128-1/runs/rank0/loaded_libraries.json`：

```json
"python_module": {
  "path": "/work/env/lib/python3.13/site-packages/deep_ep/backends/direct/__init__.py",
  "sha256": "a528b9c7c862148c0b831e8cff0b0cf746cbdbbcd2bf6c7615ac1a2145b13073"
}
```

该字段来自 `bench_v2_bandwidth.loaded_identity()`：
`python_module = file_identity(deep_ep.backends.direct.__file__)` —— 是**实际加载模块**的路径，
不是配置或猜测。所以成功任务用的是 **`/work/env` venv 里的 deep_ep**。

`/work/env/pyvenv.cfg`：`--system-site-packages` venv，`bin/python` 符号链接到
`/opt/conda/envs/hunyuan4_tenpu/bin/python`（同一解释器，但 venv 的 site-packages 优先）。

### 2.2 容器内其实有两套 `deep_ep`，代码不同、版本号相同

| 位置 | `buffer.py` sha256 | `udma_policy.py` sha256 | 读 `DEEPEP_CLOS_QP_PLANS` | `ascend_deepep` 版本 |
|---|---|---|---|---|
| `/opt/conda/envs/hunyuan4_tenpu/lib/python3.13/site-packages/deep_ep`（**精度 worker 用**） | `7ff0a945…` | `1e67a982…` | **否**（0 处） | `0.1.0.dev5` |
| `/work/env/lib/python3.13/site-packages/deep_ep`（**成功任务用**） | `7cd0d0f0…` | `94069684…` | **是**（1 处） | `0.1.0.dev5` |
| `/work/source/deep_ep`（源码快照） | `7cd0d0f0…` | `94069684…` | **是**（1 处） | — |

即 `/work/env` 装的与 `/work/source` **逐字节相同**，是比 conda wheel 更新的代码；
`importlib.metadata.version()` 两者都返回 `0.1.0.dev5`，**版本号无法区分这两套代码**。

差异点（`_prepare_shmem_bootstrap`，`/work/source` / `/work/env` 版）：

```python
qp_plans = os.environ.get("DEEPEP_CLOS_QP_PLANS", "")
if qp_plans:
    options += (("qp_plans", qp_plans),)   # 进入 8 机 all_gather 一致性 options
    key += repr(("qp_plans", qp_plans))
```

conda wheel 版没有这段，也完全没有 `DEEPEP_CLOS_QP_PLANS` 字符串。

### 2.3 成功任务显式约束了 QP 计划

`ep128_retest_20261128_091417/ep128-1/runs/rank0/session.json`：

```json
"qp_plans": "rank:16:1:1;rank:8:1:1"
```

与 `rank_sweep.run()` 里 `os.environ["DEEPEP_CLOS_QP_PLANS"] = spec` 对应。
`benchmarks/README.md` 对该变量的语义说明：

> 未设置时，自动模式从当前策略选择器生成各合法核数、行宽区间、V1/展开/非BF16 回退路径的
> **QP 并集**；显式设置本变量优先，格式 `order:P:W:Q`……**连接数量减少不等同于已测得初始化加速**。

成功任务还做了额外的编排准备（`rank_sweep.py:665-730`）：`dist.TCPStore(MASTER_ADDR, control_port, ...)`
+ `StoreGroup`、替换 `_bootstrap_all_gather` / `_validate_group_consensus`、
`store_topology_collective(group)`、预计算 `resolve_udma_policy(...).bind_group(group)`。

### 2.4 失败侧的现象

SHMEM 底层日志（attempt 2，11:27:23）：

```
Wait hcomm UDMA channel ready timeout, channelNum = 2353,
pollIntervalMs = 10, pollTimeoutMs = 300000, elapsedMs = 300005
... Async connect failed, ret = -7 ... setup_heap() failed
```

`-7` 是 **2353 个 UDMA channel 等 300 秒没建完**后的返回码，不是参数非法。

## 3. 根因（修正后）

1. 精度 worker 用容器 `PATH` 里的 conda python 直接跑，解析到 **conda site-packages 的旧版
   deep_ep**（`buffer.py 7ff0a945…`）。该版既不读 `DEEPEP_CLOS_QP_PLANS`，精度任务也没设置它。
2. 于是 auto UDMA 策略在 128 rank 下生成**全路径 QP 并集**（≈2353 个 channel），
   300 秒内建不完 → `status=-7`。
3. 成功任务解析到 **`/work/env` 的新版 deep_ep**（`buffer.py 7cd0d0f0…`），
   并显式设置 `DEEPEP_CLOS_QP_PLANS='rank:16:1:1;rank:8:1:1'`，把连接数约束到 2 组计划，
   配合 TCPStore / topology collective，能在时限内建完 → 成功。
4. 因此 **UDMA 构造参数几乎相同**（两边 `udma_auto_policy=True`、都不传显式 `udma_*`、
   都 `transport="udma"`），差异不在构造参数；也不在 bootstrap 模式（已证伪）。

## 4. 此前假设的修正记录

| 轮次 | 假设 | 判定 |
|---|---|---|
| 1 | workspace 容量 / 别人任务占卡 / deep_ep 版本 | 证伪（0.22 GiB、8 机空闲仍失败、同版本号下曾以为一致） |
| 2 | `shmem_ip_port` 缺失 → UID bootstrap 失败 | **证伪**：修复后 TCP endpoint 8 机全建通（`.4` LISTEN 29920、ESTAB 144），仍 `-7` |
| 3 | `udma_auto_policy` 自动 vs 手动 | **证伪**：`bench_dispatch_stages.py` 用 auto=True 也成功；`rank_sweep` 用 auto 成功 |
| 4 | 进程组 gloo vs TCPStore / 拓扑发现 | 非根因，属成功任务的配套编排 |
| **5（本文）** | **两套不同代码的 deep_ep + 缺少 `DEEPEP_CLOS_QP_PLANS` 约束** | **当前结论**（有产物路径 + sha + qp_plans 三重硬证据） |

修复 `shmem_ip_port` 只改了 bootstrap（交换 UID/endpoint 的方式），不影响数据面 QP 数量，
所以它「看起来生效」（TCP 链路建通）却无效。attempt 4 的 `acc_tcp_link receive header failed,
errno 4` 是 peer 超时退出后的次生现象。

## 5. 最小修复方向（理论，未执行）

按用户「deepep 就用容器内默认版本」的口径，需明确「容器内默认」其实有**两套**；
要对齐成功任务，应：

1. 让 128P 精度 worker 用 `/work/env/bin/python`，或把
   `/work/env/lib/python3.13/site-packages` 放到 `PYTHONPATH` 首位（对齐成功任务的模块解析）。
2. 8 机一致设置 `DEEPEP_CLOS_QP_PLANS='rank:16:1:1;rank:8:1:1'`（或按用例裁剪），
   并确认加载的 `buffer.py` sha 为 `7cd0d0f0…`。
3. 必要时补 `control_port` + TCPStore / `store_topology_collective`（对齐 `rank_sweep.run()`）。
4. 恢复前确认 8 机空闲；不要盲目重试。

`shmem_ip_port` 那处修复可保留（成功任务本身也传），但它不是关键项。

## 6. 对 R2 环境统一脚本的影响（仅登记，未改脚本）

`scripts/run_round2.py`（commit `35c7ac2`）里 `RUNTIME = ""`，`env_prefix()` 的 PYTHONPATH 为
`STAGE : BENCH_DIR : GOLDEN_DIR : $PYTHONPATH` —— 未包含 `/work/env/lib/python3.13/site-packages`。

建议后续按第 5 节同步修正 R2 的 python/PYTHONPATH 与 QP_PLANS；本轮未改动该脚本。
