# R3 阶段 C（EP128 泛化精度）执行方案（2026-11-28）

> 依据：[`第三轮测试执行指南_20261128.md`](./第三轮测试执行指南_20261128.md) §五、
> 用户补充「C 也带『被kill/出错继续重试』，注意精度复用统一buffer」。
> 控制器：[`scripts/r3_c_ep128/`](./scripts/r3_c_ep128/)，自动接续：[`scripts/auto_continue_c.py`](./scripts/auto_continue_c.py)。

## 1. 为什么不用 `run_round3.py precision --eps 128`

`run_round3.py` 的精度阶段是**逐 case 独立 torchrun**（每例一次进程组、每例重建
Buffer），不满足用户既定的「精度多 case 复用统一 Buffer」口径（见
`feedback_precision_buffer_reuse`）。C 因此改用持久进程组控制器：8 机 128 rank
**一个进程组**，按 `compatibility_key` 分组复用已初始化的 Buffer，组内连续 case
不重建（打印 `BUFFER_REUSED`）。性能阶段 B 保持逐例隔离口径，不受影响。

## 2. 用例与 Buffer 分组

| 项 | 值 |
|---|---|
| 用例来源 | `gen_precision_cases.py` 的 50 条规格投影到 EP128（指南 §五·C3） |
| epr 双档 | 主档 `main` epr=4（E=512，与性能/基线同口径）／探针 `probe` epr=32（E=4096，大 E 泛化），**分开报不混算** |
| API | v1 / v2 各一遍 |
| 总例数 | **200**（50 × 2 档 × 2 API） |
| Buffer 组 | **17 组**（V1 一组；V2 按 hidden/num_topk/dtype/huge_pages 分组） |
| 分组容量 | 组内取 `max_tokens` 最大值；workspace 用 EP32/EP64 校准公式以 num_ranks=128 重算 |
| 最大 workspace | **28.06 GiB**，低于 `ACLSHMEM_MAX_LOCAL_SIZE = 40 GiB`，guard 设 38 GiB |

> R2 400 例泛化 plan 的 V1 单组 workspace 是 48 GiB，正是超过 shmem 40 GiB
> 上限导致全量 `aclshmemx_init_attr ... status=-2` 的根因。本方案按 R3 的
> 50 条规格重算后降到 28 GiB，从源头规避。

## 3. 两层重试（「被 kill / 出错继续」）

| 层 | 实现 | 覆盖 |
|---|---|---|
| **内层** | `r3_c_ep128/run_retry.py`：40 次 attempt，每次 `collect_and_judge` 从 8 机容器磁盘结算已通过 case，只重跑 `remaining`；启动 `recover_completed()` 从历史 attempt 目录恢复 | worker 被 kill / 超时 / rc≠0 / 部分 rank 失败 |
| **外层** | `auto_continue_c.py` 的 `supervise_c()`：监控控制器进程 `proc.poll()`，若退出且 `status.json` 未 `completed` 就重新拉起 `run_retry.py --run`（启动即 recover，不重复已完成 case） | 整个控制器进程被 kill / 异常退出 |

产物不回传（沿用既定口径）：判据 JSON 留在容器磁盘，控制器只读不写回 NFS。

## 4. 触发条件与执行顺序

`auto_continue_c.py` 每 60s 轮询，三者全满足才触发：

1. B 阶段 perf 控制器已退出（不抢 `.6~.11`）；
2. **8 台 NPU 全 16/16 空闲**（C 需 128 卡整齐，含 `.7`）；
3. 无其它 `run_round3` / `run_retry` 控制器在跑。

触发后先重跑 `run_round3.py gate` 要求 `full_pass=True`，再启动 C。
全局执行顺序仍按指南 `gate → C → B → D → E`；B 已在 7 台空闲机先跑，
`.4/.5` 释放后自动补 C。

## 7. 判据（与指南 §五·C3 一致）

`run_retry.py` 的 `judge()` 对**每个 case 的全部 128 rank** 校验 6 项：
`result.json.precision_passed=true`、`precision_only=true`、`operators={}`、
`buffer_reused=true`、`precision.json.passed=true`、`exit.json.code=0`。
全部满足才计入 `completed`，写入 `status.json` 的 `completed` 字典。

## 10. 首次实跑失败与容量修正（2026-11-28 18:12 → 18:50）

C 于 18:12:28 由守护触发（gate `full_pass=True`），但 **attempt 1~13 全部
`rcs` 8 台全 1、`passed=0`**，是确定性错误、重试空转，已停守护与控制器。

**现象**：`run_attempt_00N_node*.log` 中 128 rank 全部报同一错误，V1 首例
（`main_ep128_v1_A_t1_h512_bf16_e0`）即挂，V2 从未到达：
```
RuntimeError: dispatch requires 326656 bytes of symmetric workspace,
              but Buffer provides 164864 bytes
  deep_ep/backends/direct/buffer.py:647 intranode_dispatch_with_plan
```

**根因**：`prepare_plan.py` 的旧 `v1_hint()` 里 `hb = align(hidden_bytes, 32)`
算了却从未参与后续运算，漏掉 V1 workspace 的主导项
`recv_buffer_tokens × hidden_bytes`，导致 V1 单组容量只按 tokens 估成
164864 B（≈161 KiB），连最小 case 的 326656 B 都不够。用 wheel 官方 API
对全部 17 组复核发现**所有组容量都被低估**（V2 各组亦差几 MiB）。

**修正**（`prepare_plan.py` 改为读权威容量表，不再用近似公式）：

| 组 | 旧值 | 官方值 |
|---|---|---|
| V1 单组（100 例一份 Buffer） | 164864 B | **34378612736 B（32.02 GiB）** |
| V2 最大组 `(7168,8,fp8)` | 30132217856 B | 30133977088 B（28.06 GiB） |

- 权威来源：PR#37 wheel 自带 `Config.get_nvl_buffer_size_hint()`（V1）与
  `ElasticBuffer.get_buffer_size_hint()`（V2）。后者正是 `elastic.py:809`
  native 校验所用的同一函数，V1 的官方 docstring 亦声明「可直接传给
  `Buffer`」，故用其返回值必过校验，不靠猜倍数。
- 容量表 [`scripts/r3_c_ep128/capacity_official.json`](./scripts/r3_c_ep128/capacity_official.json)
  由容器内官方 API 对 17 组逐一实算生成（附生成时间/来源/组 key/每组例数），
  `prepare_plan.py` 按组 key 查表并校验 `max_tokens`/`case_count` 一致，
  缺 key 或与 spec 不符直接报错，**不允许回退到近似公式**。
- 最大组 32.02 GiB，占 `ACLSHMEM_MAX_LOCAL_SIZE = 40 GiB` 的 80%，
  低于 38 GiB guard；V1 为单组一份 Buffer，不会与 V2 组累加。
- `plan.json` / `plan_smoke.json` 已据此重生成（200 例 / 17 组不变）。
- 失败的 13 次 attempt 产物（0 通过）已清理，重跑从 attempt 1 开始。

**验证（2026-11-28 19:03 / 19:06）**：

| 阶段 | 结果 |
|---|---|
| 8 例 smoke | **8/8 通过**，`FULL attempt 1 passed=8 remaining=0 rcs` 8 台全 0，`state=completed` |
| 全量 C 重启 | 19:06:00 gate `full_pass=True` → `run_retry.py --run` 200 例，`RECOVERED 0/200`、`ATTEMPT 1` |
| 全量首例 | V1 首例已 `CASE_PASSED` / `BUFFER_INITIALIZED`，`dispatch requires` 错误 0、`RuntimeError`/`Traceback` 0，128 rank 占满 8 机正常推进 |

smoke 与全量首例均确认 V1 容量修复生效、V2 组亦未再报容量错误。

> 关联：`checks_v1.py:35` 本来就用官方 `get_nvl_buffer_size_hint(hidden*2, ...)`，
> 而 `batch_worker.py:157` 的 `new_v1()` 却读 plan 里的近似值——两处口径不一致，
> 是本次错误的直接触发点。现统一为官方 API 口径。
>
> 复用版性能第 2 套（EP4/EP64 各 18 例）在 C 运行期间保持 `paused`
> （EP4 12/18 variant 已存 `round3_perf_supp_reuse.csv` checkpoint），
> C 完成、5 台空闲后按 `completed_variants()` 续跑补齐 36 例并出对比报告。

## 11. 扩为 400 例 + 组排序修复（2026-11-28 19:30 → 22:25）

用户指示「EP128 精度 400case，完成后自行完成R3剩余任务」，选择口径
**100 spec × 2 档(main/probe) × 2 API = 400 例**（保持 epr 双档与 V1/V2 分开报，
只把泛化规格从 50 扩到 100，不引入新 hidden/topk/dtype 轴值）。

- `prepare_plan.py` 新增 `extra_spec_cases()`：基础 50 条原样 + A 形状 38 条
  （A 轴 4×4×2×2=64 组合中取未用的）+ B 专家 12 条（expand 翻转）= 50 条扩展，
  **不改公共生成器** `gen_precision_cases.py` / `precision_cases_2to16p.json`
  （R2 / D 阶段口径不受污染）。400 例全部合法：100 spec、400 唯一 variant、
  hidden 全 128 倍数、topk ≤ min(128, ep·epr)。
- 容量表按新规格用容器内官方 API 重算：19 组（V1 32.02 GiB = 80% 上限，
  V2 最大 28.06 GiB），全部 ≤ 38 GiB guard。`gen_capacity_400.py` 入库可复现，
  `prepare_plan.py --emit-groups` 解决「容量表按新 plan 算 / plan 又依赖容量表」
  的循环依赖。
- 去除 `run_retry.py` / `auto_continue_c.py` 的 200 硬编码，改读
  `plan.json.case_count_total`。

**首次 400 例实跑（19:53）暴露第二个确定性问题**：plan 的 `remaining`
未排序，case 按 `v1,v2,v1,v2…` 交替 → **400 例产生 400 次 Buffer 组切换**
（应只有 19 次），每例都 destroy + 重建 32 GiB Buffer，既违背「复用统一
Buffer」口径，也让 50 例耗时 2.5 小时，并在 22:12 触发
`Hccl::NetworkApiException / HrtRaGetAsyncReqResult error[128200]` →
SIGABRT，8 台同时收 SIGTERM。checkpoint 结算 50 例后 attempt 2 续跑。

- **修复**：`prepare_plan.py` 生成 plan/smoke 时按
  `compatibility_key` 排序让同组 case 连续。校验：plan 400 例 → **19 次**
  组切换，smoke 8 例 → 3 次（原为 6 次）。variant 集合与容量不变。
- 旧 50 例 checkpoint 是「每例独立 Buffer」错误口径下跑出的，
  **不并入最终交付**：已清全部 attempt 产物（本地 + 8 机容器），
  用排序后 plan 从头跑 400 例，保证全批「组内复用」口径一致。
- `checks_v1/v2.py` 无条件写 `buffer_reused=True`（精度校验标记，非真实
  复用语义），故排序不影响 `judge()` 判据。

### 11.1 第三个确定性问题：aiv=2 非法（2026-11-28 23:33）

排序修复后 C 从头跑，attempt 1 结算 **84/400 通过**（全在
`results_attempt_001_full`），但 attempt 2~6 连续 `passed=0`、
`rcs` 全 1。根因：`checks_v1.py:34` 构造 `Config(args.num_aiv)`，
而 PR#37 wheel 的 `Config.__post_init__` 要求 `num_aiv == 0`（默认）
或「偶数且 ≥8」；spec C 组原有的 `aiv=2`（4 例）× 2 API = **8 例**
直接抛 `ValueError: communication num_aiv must be at least 8`。
200 例时代因首例即挂从未跑到；400 例排序后 V1 组先跑就撞上。

- 容器内实测 wheel `Config` 合法值：`0 / 8 / 16 / 32 / 64` 通过，`2 / 4` 失败。
  但 `bench_v2_precision.arguments` 的 `--aiv` 是
  `choices=range(2,65,2)`，**不接受 0**（第一次折成 0 后 attempt2
  报 `argument --aiv: invalid choice: '0'`，又空转）。两者交集最小值是 **8**。
- 修复：`prepare_plan.py` 的 `build_cases()` 把 `0 < aiv < 8` 折成
  `8`（同时满足 argparse 与 wheel Config），**variant 集合与 buffer
  分组不变**（aiv 不在 compatibility_key 里），容量表 19 组与
  `--emit-groups` 复核 0 处不一致；400 例全部 aiv 合法。
- 84 例 completed 全部是合法用例、与 aiv=2 的 8 例交集为 0 ⇒
  checkpoint **保留有效**：清掉 002~006 失败 attempt 目录（8 机
  `KEPT=1 OTHER_DIRS=0`），重启后 `recover_completed` 恢复 84 例，
  只补剩余 316 例。
- 另修 `run_retry.py`：外部任务占卡导致的 `preflight` busy 不再消耗
  40 次 attempt 预算（改等待 60s），避免 `.5` 上别人的 `npu_comm_bench`
  让 C 在 5 分钟内空转耗尽。编排器也去掉了会绕过 gate 的「自行拉起
  C」保底，改为纯监控，C 的启动/重启一律交给守护。

**400 例完成后自动编排**（`scripts/auto_finish_r3.py`，后台运行）：
独立监控 `status.json`（不依赖守护 8h 上限，含 C 被 kill 的保底重启），
C `completed` 后按序执行：C 结果汇总 `round3_precision_ep128.csv` →
D 精度 200 例 `round3_precision.csv` → E 异常 E4/E5 `round3_abnormal.csv` →
复用版性能续跑补齐 36 例 → 两套对比 `round3_perf_reuse_compare.csv` →
每阶段结果即时 git 上传。各阶段幂等、状态写 `round3_auto_finish.json`。
