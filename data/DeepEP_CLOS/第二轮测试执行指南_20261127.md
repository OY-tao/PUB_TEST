## 三、阶段 A：代码更新与重编译（门禁）

### A1 前置

| 项 | 值 |
|---|---|
| 节点 | node0..node3 = `30.104.128.4 / .5 / .6 / .7`，各 16 卡 |
| 接入 | `ssh -p 56000 root@<ip>`；容器名含 `deepep`（脚本自动 `docker ps` 发现） |
| 容器内 | 源码 `/workspace/deepep`，运行库 `/workspace/runtime`，bench 在 `benchmarks/clos/` |
| 关键约束 | bench **自带** torchrun（`bench_*:172` 起拼 `torch.distributed.run`），外面**不要再套 torchrun**；每节点传 `--node-rank=N` 即可 |
| 环境 | `source .../set_env.sh`；`unset SHMEM_UID_SESSION_ID ASCEND_RT_VISIBLE_DEVICES`；`SHMEM_UDMA_CONNECT_TIMEOUT_MS=300000` |

### A2 步骤

1. **同步代码**：容器内 `git -C /workspace/deepep fetch origin main && git checkout main && git pull --ff-only`。
   只用 ff-only，本地有改动就先 `git stash`——脏工作区会让 `gate` 的 `clean_worktree` 报红。
2. **重编译**：沿用上轮验证过的编译容器 / venv（CANN 9.2.1、GNU 13.3.0、cmake 3.28.3、pybind11 3.0.4、Ascend950 / Release）。
   编译产物落到**新目录**（如 `/workspace/runtime_r2`），用 `PYTHONPATH` 覆盖加载，**不要直接覆盖 `/workspace/runtime`**——
   一旦新库有问题，还能一行环境变量切回上轮运行库做对照。
3. **锁定 shmem revision**：上轮 `4ef16ef` 对比就栽在这里（锁定 `29fad12` vs 基线 `a5e55f75`，
   降幅最大的恰好是 shmem 依赖最重的 cached / combine 路径）。本轮**四机必须同一个 shmem revision**，
   并写进记录，否则 dispatch 的 delta 又无法归因。
4. **重启服务进程**：编译完成后重启所有 rank 的容器内进程，避免旧 `.so` 残留在已加载进程里。
5. **跑门禁**：`python scripts/run_round2.py gate`。

### A3 门禁看什么

`gate` 会在每台机器上采集并落盘 `round2_gate.json`：

| 检查 | 判据 | 失败含义 |
|---|---|---|
| `all_nodes_reachable` | 4/4 节点 docker/容器可用 | 有机器没起来，跑批会卡在 rendezvous |
| `single_commit` | 四机 `git rev-parse HEAD` 完全相同 | 部分机器没拉到新代码 → 结果不可用 |
| `so_identical` | `deep_ep/**/*.so` 的 sha256 字典完全一致 | 编译器/源码不一致，跨机通信行为会分叉 |
| `no_mesh_clos` | `Buffer`/`ElasticBuffer` 不来自 `mesh_clos` | 走错实现（`mesh_clos` 是另一套代码），数字全废 |
| `clean_worktree` | `git status --porcelain` 为空 | 有人手改了源码，commit 号不代表实际代码 |
| 卡空闲 | `npu-smi` 前 N 张卡 `No running processes found` | 别的任务占卡，会互相拖慢 |
| 大页 | 记录 `/proc/meminfo` 的 `HugePages_*` | 只为留证；真正关闭靠"命令行不传 `--huge-pages`" |

> `no_mesh_clos` 这一项是**一行代码就能毁掉整轮**的坑：`global_clos` 只是 `direct` 的别名入口（274 B），
> 而 `mesh_clos` 是完全独立的实现（`elastic.py` 78 KB vs `direct` 64 KB），从输出上根本看不出来。

## 四、阶段 B：性能 48 例（不开大页）

### B1 用例集

**每 EP 12 例 = 2 tokens × 3 hidden × 2 aiv**，形状与 `V2测试Case.txt` 严格一致，共 **48 例**：

| 维度 | 取值 |
|---|---|
| EP | 8 / 16 / 32 / 64（EP128 需 8 机，本轮不做） |
| num_tokens | 8192 / 16384 |
| hidden | 2816 / 6144 / 7168 |
| aiv | 32 / 64 |
| 固定 | topk=8、dtype=bf16、expand=1、route=uniform、warmup=10、iterations=30、seed=20260823 |
| experts | 全局 256 → **epr = 256/EP**（EP64 时 epr=4，路由集中是参考表设定，不是缺陷） |

### B2 波次编排（"充分利用 4 机"落在这里）

EP8 只要 8 卡、EP16 要 16 卡、EP32 要 2 机、EP64 要 4 机，且**互不重叠**，所以：

| 波次 | 编排 | 占用 |
|---|---|---|
| 第 1 波 | **EP64 × 12 例** | node0+1+2+3，每机 16 卡 |
| 第 2 波 | **EP8 × 12 ‖ EP16 × 12 ‖ EP32 × 12** | EP8→node3（8 卡）、EP16→node2（16 卡）、EP32→node0+1（各 16 卡） |

总时长 ≈ `T(EP64) + max(T(EP8), T(EP16), T(EP32))`，而不是四个 EP 串行。
**先把 EP64 跑掉**是有意的：它要求四机同时空闲，等别的任务来抢卡就再也凑不齐。

> 三个易错点：同一波内各 EP 的 master 端口不同（脚本按阶段分端口）；EP64 四节点必须**同时**启动；
> 同 case 的 `run_id` 各节点必须一致（脚本用同一串）。

### B3 口径与判定

- 只采信 `official_logical_GBps_rank_mean`，其它列（`algorithm_bytes`、`remote_payload_GBps`）只做诊断。
- dispatch 的 per-row 账本含 `topk*12`（索引/权重），combine 只含纯 payload——这是历史"dispatch 看起来慢"的口径根源，别再重算一遍。
- **判定用 delta 不用绝对值**：同一脚本、同一参数，本轮 vs 上轮 `results_20261125_*`：

| |delta| | 处置 |
|---|---|
| ≤ 3% | 视为未变（实测 rank 间 CV 中位 0.33%、最大 0.86%，3% 已留足余量） |
| 3% ~ 8% | 必须复测 1 次再下结论（单次跑批在 EP32 曾出现 −10% 级离群点） |
| > 8% | 判为变化，按 EP × op × 形状定位，先查 shmem revision 与 `.so` 一致性 |

- 已知待观察点：上轮 `dispatch` 系统性 −4.15%、`combine_weighted` −7.00%、EP64 `combine_unweighted` −17.7%。
  本轮若这些偏差**跟着复现**，说明是新代码/新库的真实差距；若**一起消失**，说明上一轮更多是环境或版本残留。

### B4 产物

`round2_perf.csv`（逐 op 一行：run_id / ep / T / H / aiv / op / gbps_mean|min|max / huge_pages=no / commit），
原始 `summary.csv` 留在容器 `<output>/<run_id>/node0/`，需要时再回传。

## 五、阶段 C：精度 200 例（EP8/16/32/64 各 50）

### C1 用例集怎么来的

**复用上轮 2-16P 的同一套 50 条规格**（`precision_cases_2to16p.json`，A 形状 20 / B 专家·topk 12 /
C AIV 6 / D 路由 8 / E FP8 4），只把 EP 与节点数投影过去：

| EP | 节点数 × 每机卡数 | 说明 |
|---|---|---|
| 8 | 1 × 8 | 与上轮同构，可直接比 |
| 16 | 1 × 16 | 与上轮同构，可直接比 |
| 32 | 2 × 16 | 上轮 EP32 是 400 例套件，本轮只取同规格 50 条 |
| 64 | 4 × 16 | 上轮 EP64 是 400 例套件（351 完成），本轮 50 条 |

用例内容（T/H/topk/epr/aiv/dtype/expand/路由）**一个字都不改**，只有 EP 和节点数变。
生成/核对：

```bash
python scripts/gen_precision_cases.py --eps 8,16,32,64 --check
python scripts/gen_precision_cases.py --eps 8,16,32,64 --suffix r2 --out .
```

EP32/64 下 `experts_per_rank` 仍是 32（全局专家 = 32×EP），**不是**性能 60 例的 epr=4——
两套用例的 epr 语义不同，别混。

### C2 执行

波次与性能相同（EP64 独占四机，其余三路并行）。每条 case 一次进程组、带 `--precision-only`；
`--api` 默认 `v2`，需要 V1 就传 `--api v1` 或 `--api v1,v2`（条数翻倍）。

### C3 通过判据（三道，缺一不可）

1. **每 rank** `precision.json.passed == true`（不是只看 rank0，也不是看进程退出码）；
2. **每 rank** `result.json` 满足 `precision_only=true` 且 `operators={}`——有性能字段说明混入了 profiling，口径被污染；
3. **全 rank digest 一致**：同一个 variant 在不同 rank 上的校验摘要必须相同，否则说明各 rank 看到的输入/路由不同。

⚠ **产物必须回传**。上轮 EP64 的 351 例和 EP32 的 294 例**只存在容器磁盘**，容器一清就永久丢失——
这是上轮唯一"不可恢复"的风险。本轮每跑完一个 EP，就把 `<output>/<run_id>/rank*/` 打包回传
（`tar` 后 `docker cp` 到宿主机，再 `scp`；不要直接往 NFS 写，会拖慢跑批）。

## 六、阶段 D：异常场景重 E4 / E5（严格按原文）

原文（`DeepEP_CLOS_yichang.txt` 第 4、5 行）：

| 场景 | 原文 | 预期 |
|---|---|---|
| E4 | 一次 dispatch，用同一个 handle combine 两次。第二次换一份同布局的专家输出 | 两次都成功，各自得到对应结果 |
| E5 | 第 1 轮 dispatch 成功，第 2 轮在所有 rank 上传**超容量输入**（非法输入），再 combine 第 1 轮 | 第 2 轮明确报错，第 1 轮仍能算对 |

### 6.1 E4：旧实现的偏离与修正

| | 旧（上轮） | 新（本轮） |
|---|---|---|
| dispatch 次数 | **2 次**（第二次用 `dispatch_cached` 复用 handle 重跑） | **1 次** |
| 第二份专家输出来源 | 第二次 dispatch 的 recv 输出 | golden 路由参考按同一 seed 生成（`delta=1`，行数/顺序相同、取值不同） |
| 判据 | 第 2 次 combine 对齐 `delta=1` 参考 | 同，但第 1 次仍对齐 `delta=0` |
| 问题 | 多了一次真实通信，等于把"handle 复用"和"再 dispatch 一次"混在一起；若 handle 被第二次 dispatch 改写，测的就不是原文语义 | 干净：只有一次 dispatch，之后两次 combine 共用同一 handle |

新实现在 `abnormal_worker_v2.py::Harness.expert_output_alt()`（纯张量，不经第二次 dispatch）。
v1 的 `abnormal_worker.py` 保持上轮原样，E4 仍是 `dispatch_cached` 版本，作对照用。

### 6.2 E5：旧口径测的是另一个缺口

| | 旧（上轮） | 新（本轮） |
|---|---|---|
| "非法输入"是什么 | `topk_idx` 填 `num_experts`（越界 expert id） | `num_tokens = num_max_tokens_per_rank + 1`（**超容量 tokens**） |
| 期望行为 | 应报错 | 应在 kernel 之前 `ValueError` |
| 实测 | **4/4 设备级崩溃**（vector core exception，进程组整体挂） | 待测 |
| 归因 | 两版**只校验 topk 宽度、不校验取值**（`elastic_v2.py:606` 只查 `num_topk > num_experts`，`:1368` 只查宽度 ≤128；`buffer_v1.py` 无取值范围校验） | 容量校验是**存在**的，见下 |

容量校验的源码位置（快照 `scripts/upstream/`）：

| 版本 | 位置 | 报错 |
|---|---|---|
| V1 | `buffer_v1.py:508-509` | `ValueError("local token count exceeds num_max_tokens_per_rank")` |
| V2 | `elastic_v2.py:1378` | `ValueError("x.size(0) exceeds num_max_tokens_per_rank")` |

⚠ **V1 的容量校验默认是关的**：`bench_v1_bandwidth.py:143` 构造 `Buffer` 时**不传**
`num_max_tokens_per_rank`，于是 `buffer_v1.py:508` 的 `is not None` 判断直接跳过。
所以 E5 要在 V1 上测"超容量被拒"，必须按文档把容量声明出来——
`abnormal_worker_v2.py` 因此构造 V1 `Buffer` 时传入 `num_max_tokens_per_rank`（`--capacity`，默认 16384），
正好等于上轮工作区实际容量。

**这本身是个结论**：bench 默认配置下，V1 的超容量输入没有任何 Python 层拦截；
只有调用方显式声明容量后才有。本轮把它写进记录，但不实际跑"未声明 + 超容量"
（那会直接越界写 workspace，只会拿到设备崩溃，得不到"是否该拦"的信息）。

越界 expert id 的旧场景在 v1 `abnormal_worker.py` 里原封不动（它的 E5 就是这个口径），
随时可用 `python scripts/run_abnormal.py --only E5` 复现上轮 4/4 崩溃。

### 6.3 判定与失败分类

| 分类 | 含义 |
|---|---|
| `passed` | E4：两次 combine 都比对通过；E5：`ValueError` 且消息含 `num_max_tokens_per_rank`，且第 1 轮 combine 仍算对 |
| `defect_suspected` | 没报错 / 报的不是容量错 / 第 1 轮结果被破坏 |
| `device_crash` | 出现 `EE9999` / `vector core` / `rtDeviceSynchronize` —— 对 E5 是**判据不符**（说明校验没拦住），必须单列 |
| `failed_runtime` | 编排/通信层问题，可重试 |

E5 与 E6 会扰动 Buffer，**各自独立进程组**（`build_groups` 已隔离），不要和 E4 塞进同一组。

### 6.4 执行矩阵

| 优先级 | 矩阵 | 次数 | 说明 |
|---|---|---|---|
| P0 | EP8（node3）、EP16（node2）× {v1,v2} × {E4,E5} | **8** | 与上轮同拓扑，可直接对照 |
| P1 | 用 v1 脚本跑 E5 对照 | +4 | 复现上轮 device_crash（越界 expert id） |
| P2 | EP32 / EP64 | +8 | 仅在四机空闲时做，异常与规模基本无关 |

## 七、执行顺序与时长

```
gate  →  perf(48)  →  precision(200)  →  abnormal E4/E5(8)
```

理由：性能最依赖"四机干净"，先跑；精度耗时最长，放中间；异常会扰动 Buffer 甚至打挂设备，
放最后，挂了也不影响前面已完成的数字。

建议按 EP 分批推进，**每个 EP 跑完立刻回传产物**：EP64（首波）→ EP8/16/32（并行波）。
单个 EP 的性能 12 例约 30~60 分钟量级（视 hidden 与 iterations），精度 50 例更长；
宁可分批，也不要攒到最后一次性回传。

## 八、风险与停止条件

| 风险 | 表现 | 处置 |
|---|---|---|
| 版本没真正更新 | `gate` 报 `single_commit=false` 或 `so_identical=false` | **停**，先修环境，不许带病跑批 |
| 走错实现 | `no_mesh_clos=false` | **停**，数字全废 |
| 四机被抢占 | `check_idle` 报卡被占 | 停当前 EP，改跑其它 EP；EP64 尤其要抢窗口 |
| 页表/大页混淆 | 有人手动加了 `--huge-pages` | 脚本 argv 断言会直接 `AssertionError`；这是故意的 |
| 精度产物丢失 | 只在容器磁盘 | 每 EP 跑完即回传，见 §5.3 |
| 异常场景打挂设备 | E5 出现 `device_crash` | 该 EP 后续 case 全部推迟，重启容器再继续；不要当成"重试即可" |
| shmem 版本漂移 | dispatch delta 忽大忽小 | 记录并核对 shmem revision，按 §A2.3 处理 |

**硬停止条件**（出现任一，本轮结论作废重来）：四机 commit 不一致 / `.so` 不一致 / 走了 `mesh_clos` /
性能跑批中有人加了 `--huge-pages`。

python scripts/run_round2.py perf --eps 8,16,32,64

#    只补某个 EP / 断点续跑
python scripts/run_round2.py perf --only-ep 64 --start 0 --limit 6

# 3) 精度 200 例（默认 v2；要 V1 加 --api v1,v2）
python scripts/run_round2.py precision --eps 8,16,32,64

# 4) 异常 E4/E5（EP8+EP16，v1+v2 共 8 次）
python scripts/run_round2.py abnormal --eps 8,16 --api v1,v2 --scenarios E4,E5

#    需要复现上轮越界 expert id 的崩溃结论（走 v1 脚本）
python scripts/run_abnormal.py --only E5

# 5) 用例清单核对（不碰设备）
python scripts/gen_precision_cases.py --eps 8,16,32,64 --check
