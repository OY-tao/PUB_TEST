# DeepEP CLOS V2 性能测试

> **被测**：`benchmarks/clos/bench_v2_bandwidth.py`
> **参考**：[OY-tao/Ascned_Test · V2测试Case.txt](https://github.com/OY-tao/Ascned_Test/blob/main/V2%E6%B5%8B%E8%AF%95Case.txt)
> **用例数**：60 个形状组合（EP × Tokens × Hidden × AIV）
> **编写**：2026-11-24

## 一、来源与范围

参考文件是 **EP8~128 的通信带宽结果汇总**，60 行 × 5 个 op 的实测值。
本文把它反推成可执行的用例规格，用于：

1. **复现**：在相同形状下重跑，与历史数据逐行对比
2. **回归**：版本升级后确认带宽没有退化
3. **扩展**：在同一套形状上补 dtype/expand 维度

⚠️ 参考表只记录结果，不含参数含义。本文的字段语义是**反推 + 代码核实**得出的，
依据写在第二节。

## 二、形状维度（已与参考表逐项核对）

| 维度 | 档数 | 取值 |
|---|---|---|
| `ep_size` | 5 | 8, 16, 32, 64, 128 |
| `num_tokens`（每 rank） | 2 | 8192, 16384 |
| `hidden` | 3 | 2816, 6144, 7168 |
| `aiv` | 2 | 32, 64 |
| `Experts`（全局） | — | EP≤64 用 256；EP=128 用 512 |

**组合数**：`5 × 2 × 3 × 2 = 60`

注意 **Experts 不是独立维度**，它由 EP 决定，所以不是 120 例。

### `Experts` 的语义（关键）

参考表的 `Experts` 列是**全局专家总数**，不是 `experts_per_rank`：

```python
experts_per_rank = Experts / ep_size
```

| EP | Experts | → `--experts-per-rank` |
|---|---|---|
| 8 | 256 | **32** |
| 16 | 256 | **16** |
| 32 | 256 | **8** |
| 64 | 256 | **4** |
| 128 | 512 | **4** |

**验证依据**：bench 的默认值是 `--ep-size 8 --experts-per-rank 32`，全局正好 256，
与参考表 EP=8 的取值吻合。

⚠️ EP=64 时 `epr=4`，意味着每卡只有 4 个专家，路由会很集中。
这不是笔误——参考表就是这么测的，复现时保持一致才能对比。

## 二·五、精度与性能是同一次运行，不能只跑性能

**结论：跑精度一定会连带跑性能；精度不过则性能也拿不到。**

bench 的 docstring 原文：*"Precision is checked before profiling."*

### 执行顺序（同一 worker 进程内，无分支）

```
worker(args)
  ├── 构造 Buffer / 造路由 / 造输入
  ├── 精度检查   _assert_equal(...)  × 5 处
  │     dispatch payload/scales、dispatch weights、dispatch indices、
  │     expert input、combine payload/weights
  ├── print("PRECISION_PASSED rank=...")     ← bench_v2:609
  └── for op in (dispatch, cached-dispatch,
                 combine_unweighted, combine_weighted):
        profiling._profile_operator(...)      ← bench_v2:633
```

`PRECISION_PASSED` 之后**直接进入 profiling 循环，中间没有任何条件判断**，
也没有 `--skip-precision` 之类的开关。

### 精度失败会怎样

`_assert_equal` 用 `torch.equal` 做**严格逐元素比较**，不等就抛 `AssertionError`：

```python
if not torch.equal(actual, expected):
    mismatch = torch.nonzero(actual != expected, as_tuple=False)
    raise AssertionError(f"{name} mismatch at {mismatch.size(0)} locations; ...")
```

抛错后 worker 中止，**profiling 那一步根本执行不到**，因此：

| 场景 | 精度结果 | 性能结果 |
|---|---|---|
| 精度通过 | PASS | ✅ 有 |
| 精度失败 | FAIL | ❌ **没有** |

**这意味着性能数据天然带有"精度已通过"的前置条件**——拿不到性能数字，
本身就说明这个形状下精度没过。

### 代价：不能"只跑性能"

如果只想看带宽、不关心精度，目前**没有官方开关**可以跳过。
每次跑都要等精度检查完成（含 CPU 侧 golden 对比，形状大时这段不短）。

可行的替代：

| 需求 | 做法 |
|---|---|
| 已跑过、想重算带宽 | `--report-only <已有output>`，**完全不启动 NPU**，只重新解析 |
| 想少跑几次 | 用 `functions` 里 4 个 op 一次性拿全，不要分 4 次跑 |
| 想缩短精度耗时 | 减小形状；精度检查的 CPU 开销随 `tokens × hidden` 增长 |

⚠️ `--report-only` 是唯一不碰 NPU 的路径，但它要求**之前完整跑过一次**
（精度须已通过、profiler 数据已在磁盘上）。

### 对用例设计的影响

1. **1148 例里每个 case 都同时产出精度与性能结论**，不是两套独立用例
2. 精度失败 = 该 case 无性能数据，统计带宽时**不能算作 0**，要单独剔除
3. 判定"性能退化"前，先确认精度是 PASS——精度不过导致的缺数据，
   不能误判成性能问题

## 三、5 个 op 与 bench 的对应

参考表的 5 列在 bench 里是 **4 个 op**（`--dtypes`/`--expand` 外的维度）：

| 参考表列 | bench op | 说明 |
|---|---|---|
| Dispatch 无权重 | `dispatch` | `topk_weights=None` |
| Dispatch 带权重 | `dispatch` | `topk_weights` 非空 |
| Cached dispatch | `cached-dispatch` | 复用 handle |
| Combine 无权重 | `combine_unweighted` | `topk_weights=None` |
| Combine 带权重 | `combine_weighted` | `topk_weights` 非空 |

⚠️ **bench 没有 `--op` 参数**，每个 case 固定跑全部 4 个 op。
所以一次调用就能拿到这 5 列的数据，无需分 5 次跑。

### 带宽口径

参考表的口径原文：

> 去重后 BF16 逻辑 payload（含本卡，不含索引及权重）÷ 通信耗时；十进制 GB/s/rank。

对应 `stage_metrics` 的 **`official_logical_GBps`**。

⚠️ **不是 `remote_payload_GBps`**（那个排除本卡）。两者差约 15%（含 self），
对不上历史数据时先查这里。

## 四、拓扑：每节点最多 16 卡

bench 硬约束 `local_world_size ∈ 1..16`，所以各 EP 所需机器数：

| EP | nnodes | 每节点卡 | 说明 |
|---|---|---|---|
| 8 | 1 | 8 | 单机 |
| 16 | 1 | 16 | 单机，卡数上限 |
| 32 | 2 | 16 | 两机 |
| 64 | 4 | 16 | 四机 |
| 128 | 8 | 16 | 八机 |

`nnodes` 由 `ep_size // 16` 自动决定（bench 也这么算，见 `bench_v2:118-119`）。

## 四·五、bench 的默认配置参数（全部核实自源码）

**不带任何参数直接运行时，bench 用的是这套默认值。**

### 形状与规模

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--num-tokens` | **8192** | 每 rank 的 token 数 |
| `--hidden` | **6144** | 隐藏维，需 128 的倍数（FP8 要求） |
| `--num-topk` | **8** | 每 token 选几个专家 |
| `--experts-per-rank` | **32** | 每卡专家数，全局 = ep × epr |
| `--ep-size` | **8** | 单机 8 卡 |

默认下全局专家 = `8 × 32 = 256`，与参考表 EP=8 那一行完全一致。

### 维度展开（决定跑几个 case）

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--dtypes` | **`bf16 fp8`** | **两个都跑** |
| `--expand` | **`0 1`** | **两种布局都跑** |
| `--aiv` | **`[32]`** | 只跑 32 核 |

⇒ **默认一次调用跑 4 个 case**：`2 dtype × 2 expand × 1 aiv`

每个 case 内部固定跑 4 个 op，所以合计 **16 次 op 测量**。
且每个 case 都会**重建 torchrun 进程组**（docstring: *"Each dtype/expand/AIV configuration gets a fresh torchrun group"*）。

### 测量参数

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--warmup` | **10** | 预热迭代数 |
| `--iterations` | **30** | 计时迭代数 |
| `--flush-l2-cache` | **True** | 每次计时前用 256 MB 缓冲清 L2；用 `--no-flush-l2-cache` 关闭 |
| `--combine-bias` | **`none`** | weighted combine 不传 bias；`two` 复现老 benchmark |
| `--seed` | **20260823** | 路由随机种子，决定 case 内容 |
| `--case-timeout` | **1800** 秒 | 单 case 超时 |

### 路由

| 参数 | 默认值 |
|---|---|
| `--route-mode` | **`uniform`**（另可选 `rank_hotspot` / `local_group`） |
| `--route-skew` | `2.0`（仅 rank_hotspot 生效） |
| `--route-hotspot` | `0`（仅 rank_hotspot 生效） |
| `--route-group-size` | `None`（仅 local_group 生效） |
| `--route-local-fraction` | `0.8`（仅 local_group 生效） |
| `--route-mask-rate` | `0.0`（叠加参数，非独立模式） |

### 拓扑

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--nnodes` | **None** → 自动 `max(1, ep_size // 16)` | EP≤16 单机；EP32→2 机 |
| `--node-rank` | `0` | |
| `--master-port` | **29500** | bench 会另占 29501 |
| `--rendezvous-timeout` | `300` 秒 | |
| `--collection-timeout` | `600` 秒 | |
| `--first-device` | `0` | 起始物理卡 |

### 其他

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--huge-pages` | **False**（不开启） | 开启后用 1 GiB SHMEM 页 |
| `--output` | `bandwidth_<时间戳>` | 自动按当前时间命名 |

### 默认配置的实际开销

单 rank 输入规模（`tokens=8192, hidden=6144`）：

| dtype | payload | scales |
|---|---|---|
| bf16 | 96.0 MB | — |
| fp8 | 48.0 MB | 1.5 MB |

4 个 case × 4 个 op × (10 warmup + 30 iterations)，且每个 case 重建进程组，
**默认一整轮下来不短**。只想快速验证链路时，建议先缩形状：

```bash
python benchmarks/clos/bench_v2_bandwidth.py \
    --num-tokens=1024 --hidden=512 --num-topk=2 \
    --dtypes=bf16 --expand=0 \
    --output=/tmp/smoke
```

### 多机（EP=32/64/128）

**每台都要跑同一个脚本**，用环境变量区分节点：

```bash
# 以 EP=32 为例（2 机）
# 在 30.104.128.4：
NODE_RANK=0 bash perf_batches/perf_ep32.sh
# 在 30.104.128.6：
NODE_RANK=1 bash perf_batches/perf_ep32.sh
```

`MASTER_ADDR` 默认 `30.104.128.4`，可用环境变量覆盖：

```bash
MASTER_ADDR=<ip> NODE_RANK=<n> bash perf_batches/perf_ep32.sh
```

**三个必查项**：

| 项 | 说明 |
|---|---|
| 两机同时启动 | 先启动的一方会等另一方，看起来像卡住 |
| `run_id` 两机相同 | 脚本已按 `${run_id}` 自动生成，同序号即同 run-id |
| 两个端口都通 | `master-port`(29500) **和** `master-port+1`(29501) |

### 断点续跑

```bash
bash perf_batches/perf_ep32.sh 5    # 从第 5 条开始
```

## 六、判定

### 与历史数据对比

同一形状下，新测带宽与参考表的偏差应满足：

| 条件 | 阈值 |
|---|---|
| 同版本、同硬件 | ±3% 内 |
| 版本升级 | ±5% 内，超出需解释 |
| 硬件或拓扑不同 | **不可直接比** |

**必须核对 6 项一致**才能横向对比：硬件型号、卡数、CANN 版本、
`route_mode`（参考表推测为 uniform）、`iterations`/`warmup`、拓扑。

### 数据合理性

| 检查 | 期望 |
|---|---|
| `device_span_us ≥ device_sum_us` | 必须 |
| `GBps ≤ 理论线速` | 必须 |
| `route_sha256` 可复现 | 同种子同路由 |
| 变异系数 CV < 5% | 稳定性 |

## 七、与 1148 例泛化测试的关系

两套用例**目标不同，不重复**：

| | 本文（60 例） | 泛化测试（1148 例） |
|---|---|---|
| 目标 | 复现历史性能数据 | 探索覆盖边界与异常 |
| 形状 | 固定 60 个，对齐参考表 | A 组 700 例，25 档 tokens 加密扫描 |
| dtype | 只 bf16 | bf16 + fp8 |
| expand | 只 1 | 0 + 1 |
| EP | 8~128（含多机） | 主要以 8 为主 + D 组拓扑 |
| 产出 | 与历史对比的带宽值 | 覆盖率与缺陷 |

**先跑 60 例性能用例**确认基线正常，再跑 1148 例泛化。顺序反了会浪费大量时间在
错误配置上。
